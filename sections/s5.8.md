Un lenguaje con tipos estáticos comprueba los argumentos de cada llamada. La
pregunta es si comprueba con el mismo rigor los otros caminos por los que un
valor llega a un parámetro. En Residuum hay dos caminos más, además de la
aplicación posicional (@sec:s5.7):

- los bindings de un RuleUse, dentro de un Program;
- los bindings de una consulta, en la cláusula `with`.

Esta sección muestra que ambos se validan contra los tipos de los parámetros,
antes de buscar, y que `with` tiene reglas de ámbito propias.

## Los mismos tipos para todos los bindings

Un binding de RuleUse se elabora como un término. El elaborador infiere su
tipo y lo compara con el del parámetro de la regla. Un binding de consulta
sigue el mismo camino. Su valor usa la gramática de términos de Formal:

- constantes del módulo;
- `after(tau)` y constructores temporales anidados;
- records;
- `none`, que recibe el tipo opcional esperado.

Los valores temporales pasan por la conversión canónica de @sec:s5.2. Un
identificador a la derecha se resuelve como constante del módulo. Un
parámetro de la consulta con el mismo nombre no lo captura. La sintaxis de
consulta no admite variables ni enumeración existencial.

Hay una diferencia deliberada entre los caminos. Un binding con nombre, de
RuleUse o de consulta, admite subtipos de entidad: un `Buyer` vale donde se
espera un `Person` (@sec:s4.3). La aplicación posicional de reglas y de
Programs exige igualdad exacta de tipos. La documentación lo registra como una
frontera de la API existente, no como una política nueva.

Toda esta validación ocurre al elaborar. No hay búsqueda, ni hipótesis, ni
cierre en ese paso. Un binding mal tipado detiene la consulta antes de que
empiece.

## Reglas de ámbito para with

Un binding de consulta es una restricción. Nunca es un seed, ni una hipótesis
que entre en Known, ni un cambio del módulo. `run` y `explain` lo ignoran:
evalúan el módulo original. Su alcance depende del ámbito de la consulta:

- `with` exige `using`; sin ámbito explícito no hay bindings;
- con `using rules { r }`, un binding `rule r.x = c` nombra un parámetro de la
  regla original;
- con `using program P`, un binding `program P.x = c` nombra un parámetro
  compartido que siga libre en `P`;
- un binding `rule r.x` también sirve dentro de un Program: el compilador lo
  traduce a través del RuleUse correspondiente.

El ámbito es exacto. Las dependencias de las reglas elegidas no se añaden
solas. La identidad de un Program es la resuelta. Un alias aplicado parcialmente
cuenta, por tanto, como Program propio. Dos reglas ordinarias no
comparten un binding porque sus parámetros se llamen igual.

La validación rechaza como error estos casos:

- un ámbito o un parámetro desconocido o duplicado;
- una constante desconocida o un valor de tipo incorrecto;
- un binding fuera del ámbito seleccionado;
- un binding duplicado;
- un conflicto con el objetivo o con un valor ya fijado en un RuleUse.

```res {#lst:s5-8-fuera caption="Un binding fuera del ámbito seleccionado" run=expect-error cmd=query}
module Fuera

entity Person
entity Thing

const ana : Person
const bob : Person
const libro : Thing
const tau : PropositionTime

seeded verb sells(seller : Person, object : Thing, buyer : Person)
seeded verb donates(donor : Person, object : Thing, donee : Person)
derived verb owns(owner : Person, object : Thing)

rule sale(seller, object, buyer, t) =
    sells(seller, object, buyer) @ t <= owns(buyer, object) @ after t

rule gift(donor, object, donee, t) =
    donates(donor, object, donee) @ t <= owns(donee, object) @ after t

experiment outside {
    seeds {}
    query residual owns(bob, libro) @ after tau
    using rules { sale }
    with { rule gift.donor = ana }
}
```
::: explanation
La consulta elige sólo la regla `sale`, pero el binding nombra un parámetro de
`gift`. La regla `gift` existe y su parámetro `donor` tiene el tipo correcto.
Aun así, la validación rechaza el binding, porque `gift` está fuera del ámbito
elegido. El error aparece antes de cualquier búsqueda.
:::

@Lst:s5-8-fuera muestra que el ámbito no es una sugerencia. Un binding sólo
puede restringir reglas que la consulta va a usar. Si la consulta aceptara el
binding y lo ignorara, el autor creería haber fijado un valor que no fijó.

## Bindings parciales

Los bindings no tienen que cubrir todos los parámetros. Una consulta con
bindings parciales se elabora bien. Si la búsqueda llega a una regla con
parámetros que ni el objetivo ni los bindings determinan, devuelve un error que
enumera esos parámetros con su tipo. No enumera valores ni descarta la regla
en silencio.

Las consultas `fourFusion` con ámbito usan la misma selección y la misma
validación, con una exigencia mayor: todo parámetro que mencione un cuerpo del
ámbito necesita binding (@sec:s6.10).

Queda una frontera documentada para los records. En el código fuente, un
record literal se normaliza al orden de su declaración. La API tipada de Rust,
en cambio, conserva el orden en que se suministran los campos.
