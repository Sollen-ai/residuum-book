Una consulta residual devuelve una fórmula (@sec:s6.8). Esta sección pregunta
qué objeto matemático denota esa fórmula. También pregunta cuándo dos
programas significan lo mismo. Las dos respuestas son órdenes parciales, que
se dibujan como diagramas de Hasse [@davey2002introduction]. Cómo se busca y
se certifica un requisito es tema de @sec:s6.8; aquí sólo importa su
significado.

Las cifras de esta sección vienen de dos fuentes. Los teoremas generales
vienen de `docs/legal-ontology-order-geometry.md`. Las enumeraciones vienen del
estudio `residuum-diagrams`, en su commit `ac4727f`. Ese estudio ejecutó
Residuum en `f3c8df3`, un antecesor de `d4d2282`. Los listados de la sección
se ejecutan, en cambio, en `d4d2282`.

## Un agente que decide si envía

El ejemplo es un agente que decide si envía una respuesta. Tres hechos pueden
llegar como seeds:

- `checked`: la respuesta pasó una comprobación;
- `lowConfidence`: la confianza del modelo es baja;
- `cached`: la memoria guarda una respuesta ya validada.

Dos verbos son derivados: `verified` y `send`. Seis reglas los relacionan.

```res {#lst:s6-14-cierres caption="El agente y el cierre de cuatro evidencias" run=run}
module Envio

const tau : PropositionTime

seeded verb checked()
seeded verb lowConfidence()
seeded verb cached()
derived verb verified()
derived verb send()

rule sendCheckedLowConfidence(t) = checked() @ t & lowConfidence() @ t <= send() @ t
rule sendCached(t) = cached() @ t <= send() @ t
rule refuseLowConfidence(t) = lowConfidence() @ t <= ~send() @ t
rule sendCachedChecked(t) = cached() @ t & checked() @ t <= send() @ t
rule verifyChecked(t) = checked() @ t <= verified() @ t
rule sendVerified(t) = verified() @ t <= send() @ t

experiment nothing {
    seeds { }
    query residual send() @ tau
}

experiment onlyChecked {
    seeds { checked() @ tau, }
    query residual send() @ tau
}

experiment onlyCached {
    seeds { cached() @ tau, }
    query residual send() @ tau
}

experiment checkedLowConfidence {
    seeds { checked() @ tau, lowConfidence() @ tau, }
    query residual send() @ tau
}
```
::: explanation
El módulo traduce a nombres legibles el ejemplo del estudio
`residuum-diagrams`. `run` calcula el cierre de cada evidencia y no ejecuta la
consulta residual. Sin seeds, Known queda vacío. La comprobación sola llega a
`send` a través de `verified`. Con baja confianza, Known contiene a la vez
`send` y `~send`, y ninguno borra al otro.
:::

Escribimos `C_P(S)` para el cierre de la evidencia `S` bajo el programa `P`.
Es el `Close_R(S)` de @sec:s6.3. `E` es el universo del ejemplo: los cinco
eventos positivos y `~send`, todos en `tau`. Un `~send` es otro evento, no la
ausencia de `send` (@sec:s6.4).

## Los estados cerrados
<!-- covers: 1 -->

En @lst:s6-14-cierres, `{checked}` se cierra en `{checked, verified, send}`.
Ese conjunto ya no crece: es un estado cerrado. En cambio,
`{checked, verified}` no es cerrado, porque le falta `send`. Un estado `F` es
cerrado cuando `C_P(F) = F`.

`docs/legal-ontology-order-geometry.md` clasifica como **THEOREM** que los
estados cerrados forman un retículo completo:

```text
F ∧ G = F ∩ G      F ∨ G = C(F ∪ G)      mínimo = C(∅)      máximo = E
```

El meet de dos cerrados es su intersección. La unión, en cambio, puede no
ser cerrada; por eso el join vuelve a cerrar. El documento enuncia el teorema
para las reglas jurídicas que inspecciona. Antes establece que su cierre es
extensivo, monótono e idempotente. Esas tres leyes valen para todo cierre
Horn: son la garantía T5 de @sec:s6.3. Con ellas, los puntos fijos de un
cierre forman siempre un retículo completo [@davey2002introduction].

## El requisito como conjunto ascendente
<!-- covers: 2 -->

Desde `{checked}` el programa concluye `send`, y desde `{cached}` también.
Desde `{lowConfidence}`, no. Añadir evidencia nunca retira `send`. Por eso las
evidencias suficientes forman una familia cerrada hacia arriba.

El requisito de un objetivo `G` bajo `P` reúne las evidencias seeded desde las
que `P` concluye `G`:

```text
Req_P(G) = { S ⊆ Seeded : G ∈ C_P(S) }
```

Una familia es un conjunto ascendente si, al contener `S`, contiene todo
superconjunto de `S`. Para un conjunto `H`, `↑H` es la familia de los
superconjuntos de `H`. El mismo documento clasifica como **THEOREM** que el
requisito es ascendente. En el caso finito vale además:

```text
Req_P(G) = ⋃ { ↑H : H ∈ Min(Req_P(G)) }
```

`Min` da los soportes mínimos. Ninguno contiene a otro: forman una anticadena.
No tiene por qué haber uno solo. En el ejemplo, `Req(send)` tiene dos soportes,
`{checked}` y `{cached}`. Su intersección es vacía y no basta. `Req(~send)`
tiene uno: `{lowConfidence}`.

## El álgebra de los requisitos
<!-- covers: 3 -->

Los conjuntos ascendentes se ordenan por inclusión. Subir es admitir más
evidencias. La intersección y la unión de dos de ellos vuelven a ser
ascendentes. Con `⊥ = ∅` y `⊤` igual a todas las evidencias, forman un álgebra
de Heyting [@davey2002introduction]. Su implicación es:

```text
U → V = { S : todo S' ⊇ S que está en U está en V }
```

`U → V` es el mayor conjunto ascendente `W` que cumple `W ∩ U ⊆ V`. Con tres
seeds hay 20 conjuntos ascendentes y 32 aristas de Hasse (@fig:s6-14-requisitos).
El estudio comprueba las leyes de Heyting en los 8.000 triples. 18 de los 20
elementos no tienen complemento, así que el álgebra no es booleana. Estas
cifras son un **MODEL RESULT** de esa instancia.

El caso que importa es `U = ↑S`. Un `X'` contiene a `X` y a `S` si y sólo si
contiene a `S ∪ X`. Como `V` es ascendente, queda:

```text
↑S → V = { X : S ∪ X ∈ V }
```

Es lo que falta, dado `S`, para entrar en `V`. El estudio lee la fórmula de
`query residual` como un conjunto de evidencias:

- un evento `x` denota `↑{x}`;
- `⊗` denota la intersección;
- `∨` denota la unión;
- `I` denota `⊤`;
- la ausencia de explicación denota `⊥`.

Así leída, la respuesta desde `S` denota `↑S → Req_P(G)`. El estudio lo
comprobó con la CLI en 1.024 casos: 64 programas, dos objetivos y ocho
evidencias. Es una **EXPERIMENTAL OBSERVATION**, no un teorema.

```res {#lst:s6-14-residuo caption="La respuesta residual desde tres evidencias" run=query setup=s6-14-envio}
experiment nothing {
    seeds { }
    query residual send() @ tau
}

experiment onlyChecked {
    seeds { checked() @ tau, }
    query residual send() @ tau
}

experiment checkedLowConfidence {
    seeds { checked() @ tau, lowConfidence() @ tau, }
    query residual send() @ tau
}
```
::: explanation
El setup oculto es el módulo de @lst:s6-14-cierres sin sus experimentos. Sin
seeds, la fórmula denota `↑{checked} ∪ ↑{cached}`, que es `Req(send)`. Las
ramas con dos seeds caen dentro de esas dos y no cambian el conjunto. Desde
`{checked}` y desde `{checked, lowConfidence}`, una rama es `I`: no falta nada.
:::

En @lst:s6-14-residuo, cada fórmula denota el conjunto correcto. Ninguna está
reducida a la anticadena. Desde `∅` quedan ramas subsumidas por `checked` o por
`cached`. Desde `{checked}`, la rama `I` ya vale `⊤`, y aun así se imprimen
otras. La consolidación del `Join` sólo elimina árboles idénticos
(@sec:s6.8).

Esta lectura es un modelo. En él, `⊗` coincide con la intersección e `I` es el
máximo. El contrato algebraico del núcleo no adopta en general ninguna de las
dos identidades (@sec:s6.7). El código tampoco tiene la implicación de Heyting
como operación. Aparece sólo como comportamiento de la consulta.

## El orden entre programas
<!-- covers: 4 -->

Los programas `{verifyChecked, sendVerified}` y
`{sendCheckedLowConfidence, verifyChecked, sendVerified}` concluyen lo mismo
desde toda evidencia. Sus textos difieren; su significado, no. El orden entre
programas compara lo que concluyen:

```text
P ≤ Q  si y sólo si  C_P(S) ⊆ C_Q(S) para todo S ⊆ E
```

La relación es un preorden. Dos programas son equivalentes si cada uno está
por debajo del otro. El cociente extensional agrupa los programas
equivalentes en clases. Su mínimo es la clase del programa vacío.

El join de dos clases es la unión de sus reglas. El estudio lo marca como
inferido con prueba, que aquí se clasifica como **THEOREM**. La unión está
por encima de cada parte, porque más reglas nunca concluyen menos. Supongamos
ahora `P ≤ R` y `Q ≤ R`. `C_R(S)` es un punto fijo de `C_R`, así que
`C_P(C_R(S)) ⊆ C_R(S)`. Por tanto, `C_P` no le añade nada, y `C_Q` tampoco.
Un estado cerrado bajo `P` y bajo `Q` lo está bajo `P ∪ Q`. Como contiene `S`,
contiene también `C_{P∪Q}(S)`.

El meet existe, porque el cociente es finito. Pero no es la intersección de
reglas. Por ejemplo, `{sendCheckedLowConfidence}` está por debajo de
`{verifyChecked, sendVerified}`. Su intersección es el programa vacío. Sin
embargo, su meet es la clase de `{sendCheckedLowConfidence}`, que sí concluye
`send` desde `{checked, lowConfidence}`.

reglas hay 16 programas, 14 clases, 25 aristas y altura 4. Las cifras son un
**MODEL RESULT** de esa instancia.

La prueba del join evalúa `C_P` en un estado con eventos derivados. La CLI no
acepta seeds derivados. Si `S` sólo recorre evidencia seeded, el orden cambia:
`{sendVerified}` equivale al programa vacío, y la unión deja de ser el
supremo (**EXPERIMENTAL OBSERVATION**). Los listados de @sec:s6-14-coop
reproducen ese testigo para la evidencia `{checked}`. El teorema de contextos resuelve el problema. Para un conjunto `D` de
eventos derivados, el contexto `A_D` añade un axioma `I <= x` por cada `x` de
`D`. El lema dice:

```text
C_{P ∪ A_D}(S₀) = C_P(S₀ ∪ D)
```

De ahí, `P ≤ Q` sobre todo `E` si y sólo si `C_{P∪A}(S₀) ⊆ C_{Q∪A}(S₀)` para
todo contexto `A` con cabezas derivadas y toda evidencia seeded `S₀`. El
estudio demuestra el lema y el teorema (**THEOREM**). La CLI con contextos
coincidió con el cierre de referencia del estudio en 1.024 de 1.024 estados
(**EXPERIMENTAL OBSERVATION**). El precio es un fixture por cada subconjunto
de derivados.

## Las reglas cooperan {#sec:s6-14-coop}
<!-- covers: 5 -->

Ni `verifyChecked` ni `sendVerified` llevan por sí solas de `{checked}` a
`send`. Juntas, sí.

```res {#lst:s6-14-solo-verificar caption="Sólo verifyChecked" run=run setup=s6-14-verbos}
rule verifyChecked(t) = checked() @ t <= verified() @ t

experiment onlyChecked {
    seeds { checked() @ tau, }
    query residual send() @ tau
}
```
::: explanation
El setup oculto declara el módulo, `tau` y los cinco verbos, sin reglas. Con
sólo `verifyChecked`, la comprobación produce `verified`. Ninguna regla lleva
de `verified` a `send`.
:::

```res {#lst:s6-14-solo-enviar caption="Sólo sendVerified" run=run setup=s6-14-verbos}
rule sendVerified(t) = verified() @ t <= send() @ t

experiment onlyChecked {
    seeds { checked() @ tau, }
    query residual send() @ tau
}
```
::: explanation
Con sólo `sendVerified`, la comprobación no produce nada. La regla espera
`verified`, que nadie deriva y que la CLI no acepta como seed.
:::

```res {#lst:s6-14-juntas caption="verifyChecked y sendVerified juntas" run=run setup=s6-14-verbos}
rule verifyChecked(t) = checked() @ t <= verified() @ t
rule sendVerified(t) = verified() @ t <= send() @ t

experiment onlyChecked {
    seeds { checked() @ tau, }
    query residual send() @ tau
}
```
::: explanation
Con las dos reglas, Known contiene `checked`, `verified` y `send`. La unión de
los dos cierres anteriores no contiene `send`. El cierre de la unión de reglas
supera así la unión de los cierres.
:::

Los tres listados muestran que el cierre de una unión de reglas puede superar
la unión de los cierres. Sobre los 64 programas de las seis reglas, eso ocurre
en 1.360 triples de programa, programa y evidencia (**MODEL RESULT**).

Con el requisito, tomado aquí sobre todo `E`, pasa lo mismo. La función que
lleva cada programa a `Req_P(send)` es monótona; el estudio lo demuestra (**THEOREM**). Pero no
preserva joins. Con las cuatro reglas de @fig:s6-14-programas falla en 16
pares no ordenados de programas (**MODEL RESULT**). En todos aparece el mismo
soporte nuevo, `{checked}`. En cada par, uno de los programas tiene
`verifyChecked` sin `sendVerified`, y el otro al revés. `explain` confirma que
la única prueba usa una regla de cada programa (**EXPERIMENTAL OBSERVATION**).

La cooperación también produce lo contrario: programas distintos con el mismo
significado. @Fig:s6-14-programas tiene dos clases con dos programas. En ambas,
`sendCheckedLowConfidence` sobra junto a la cadena `verifyChecked`,
`sendVerified`. Ninguna regla la subsume por su texto. Entre las seis reglas
hay también un caso textual: `sendCached` subsume a `sendCachedChecked`. Por
eso `{sendCached}` equivale a `{sendCached, sendCachedChecked}`. El cociente es
extensional: compara eventos, no justificaciones. Desde
`{checked, lowConfidence}`, `explain` da a `send` una justificación con
`{verifyChecked, sendVerified}` y dos al añadir `sendCheckedLowConfidence`
(**EXPERIMENTAL OBSERVATION**).

## Fidelidad
<!-- covers: 6 -->

Un solo requisito no basta para reconocer un programa. El programa vacío y
`{verifyChecked}` tienen el mismo requisito para `send`. Con las cuatro
reglas, `Req_P(send)` separa sólo 10 de las 14 clases (**MODEL RESULT**).

La familia de requisitos de todos los eventos, en cambio, basta. Se toma aquí
`Req_P(x)` sobre todo `E`. Por definición, `x ∈ C_P(S)` si y sólo si
`S ∈ Req_P(x)`. Por tanto:

```text
C_P(S) = { x ∈ E : S ∈ Req_P(x) }
```

La familia determina el cierre y, con él, la clase del programa. Además,
`[P] ≤ [Q]` si y sólo si `Req_P(x) ⊆ Req_Q(x)` para todo `x`. El estudio lo
demuestra (**THEOREM**) y lo comprueba en las 14 clases y 64 estados
(**MODEL RESULT**). En el ejemplo, `Req(verified)` separa el programa vacío de
`{verifyChecked}`.

El par `(p, n)` que el cierre asigna a un objetivo en `S` lee dos de estos
requisitos: `p` dice si `S` está en `Req_P(G)`, y `n` si está en `Req_P(~G)`.
Es la valoración del cierre Horn, no el modelo mínimo FOUR, que puede derivar
más (@sec:s6.10, @sec:s6.12).

## El cierre como alcanzabilidad
<!-- covers: 7 -->

Las reglas del ejemplo también se leen como un grafo, aunque de un tipo
especial. Cada evento es un nodo. Cada regla es una hiperarista: va de un
conjunto de premisas a una conclusión [@gallo1993directed]. Una regla de una
premisa es una arista corriente. Una regla de dos premisas sólo se recorre si
se alcanzan las dos (@fig:s6-14-hipergrafo). Esta lectura es del libro; los
documentos de Residuum no la enuncian.

```dot {#fig:s6-14-hipergrafo caption="Las seis reglas del agente como hipergrafo. Las flechas llevan el nombre abreviado de la regla. Dos puntos negros juntan pares de premisas: checked con lowConfidence y cached con checked; de cada punto sale una flecha a send."}
digraph {
  rankdir=BT; nodesep=0.35; ranksep=0.45;
  node [shape=box, fontname="DejaVu Sans", fontsize=10, margin="0.06,0.03", height=0.25];

```

Los nodos alcanzables desde `S` forman el menor conjunto con dos
propiedades. Contiene `S`. Si contiene las premisas de una hiperarista,
contiene su conclusión. Gallo y sus coautores llaman a esto B-conexión. Es la
definición de `C_P(S)` como menor punto fijo (@sec:s6.3). El algoritmo de
Dowling y Gallier recorre así las cláusulas Horn en tiempo lineal
[@dowling1984linear].

El requisito cambia la pregunta. `Req_P(G)` reúne los conjuntos de seeds desde
los que `G` es alcanzable. Un soporte mínimo es un origen del que `G` es
alcanzable y del que ningún subconjunto propio lo es. Desde `{checked}`, el
camino pasa por `verified`. Desde `{cached}`, basta la arista `sendCached`.

En un grafo corriente, una arista basta para llegar a un nodo. Ese grafo sólo
expresa la disyunción. Si todas las reglas tuvieran una premisa, cada soporte
mínimo tendría a lo sumo un seed. La conjunción de premisas pide hiperaristas.

La lectura alcanza también al orden entre programas. Dos programas
equivalentes son dos hipergrafos con la misma alcanzabilidad. La fórmula de
la fidelidad dice lo mismo: la familia de requisitos es esa relación de
alcanzabilidad. La cooperación de @sec:s6-14-coop es un camino que necesita
aristas de los dos programas.

La lectura tiene límites:

- una regla con parámetros es un esquema de hiperaristas; el hipergrafo es el
  de las reglas instanciadas, y con tiempos como `after tau` puede ser
  infinito (@sec:s6.3);
- `~send` es un nodo más, así que la lectura vale para la valoración del
  cierre Horn y no para el modelo mínimo FOUR;
- un default bloqueado retira una conclusión, y la alcanzabilidad nunca
  retira nada; los defaults quedan fuera (@sec:s6.9).

El runner no recorre este hipergrafo antes de cerrar. Su grafo de verbos olvida
