Un programa Residuum describe un dominio con pocos tipos de datos. Las
entidades dan nombre a las clases de objetos. Los records agrupan valores con
nombre. Los conjuntos y los opcionales completan el repertorio. Esta sección
presenta cada uno y dice qué valores admite. Cómo se evalúan esos valores en
el cierre corresponde a la Parte 6 (@sec:s6.4).

## Entidades con campos

<!-- covers: 1 -->

Una entidad es un tipo nominal. Se declara con `entity` y, si hace falta, con
una lista de campos:

```text
entity Thing
entity Person {
    assets : Set Thing
}
```

Cada campo tiene un nombre y un tipo. El tipo de un campo puede ser:

- otra entidad, como `owner : Person`;
- un conjunto, como `assets : Set Thing`;
- un opcional, como `thing : Thing?`;
- `PropositionTime`, como `first : PropositionTime`.

Los campos pueden nombrar entidades declaradas más abajo en el mismo módulo.
El resolver de módulos admite esas referencias locales hacia delante. En
cambio, un tipo que no corresponde a ninguna entidad declarada o importada es
un error (`unknown entity`). Una mención de tipo nunca crea una entidad por sí
sola.

Una entidad tiene dos clases de valores. La primera son las constantes con
nombre, como `const juan : Person`. Una constante es una identidad opaca: dos
constantes distintas son siempre valores distintos. La segunda son los
records, que se describen a continuación. Una constante y un record son
términos distintos, aunque tengan el mismo tipo.

## Records y orden canónico de los campos

<!-- covers: 2 -->

Un record es un valor estructurado de una entidad con campos. Se escribe con
el nombre de la entidad y un valor para cada campo:

```text
Slot { first = tau, second = after(tau) }
```

La elaboración aplica cuatro reglas al literal:

- cada campo declarado debe aparecer, o el error es `missing field`;
- ningún campo puede repetirse (`duplicate field`);
- no puede aparecer un campo que la entidad no declara (`unknown field`);
- cada valor debe ser asignable al tipo del campo.

La comprobación del valor de un campo es estricta. Acepta el tipo exacto y,
para un campo opcional, también `none` o un valor del tipo interior. No acepta
un subtipo (@sec:s4.3).

La referencia del lenguaje dice que el orden de los campos no importa. La
razón está en el elaborador. Recorre los campos en el orden de la
declaración, no en el orden escrito. Así, dos literales con los mismos campos
en distinto orden producen el mismo término del TypedAST. @Lst:s4-2-orden lo
comprueba con un seed y un objetivo escritos en órdenes distintos.

```res {#lst:s4-2-orden caption="Dos órdenes de campos, un solo valor" run=run}
module Registros

entity Thing
entity Person {
    assets : Set Thing
}
entity Slot {
    first : Person
    second : Person
    extra : Thing?
}

const ana : Person
const bob : Person
const tau : PropositionTime

seeded verb booked(slot : Slot)
derived verb confirmed(slot : Slot)

rule confirm(slot, t) = booked(slot) @ t <= confirmed(slot) @ t

experiment twoOrders {
    seeds { booked(Slot { second = bob, extra = none, first = ana }) @ tau, }
    query residual confirmed(Slot { first = ana, second = bob, extra = none }) @ tau
}
```
::: explanation
El seed escribe `second` primero y el objetivo escribe `first` primero. La
elaboración ordena los dos literales según la declaración de `Slot`. Por eso
la regla `confirm` concluye exactamente el objetivo y la línea `Horn` dice
`true`. La salida abrevia cada record como `Slot {...}`. El campo opcional
`extra` recibe `none` en ambos literales.
:::

El orden canónico es una propiedad de la elaboración del código fuente. No es
una propiedad de la igualdad de términos. Dentro del TypedAST, la igualdad y
el matching comparan los campos por posición, con sus nombres. Un record
construido desde Rust con los campos permutados es otro valor. Los documentos
de Residuum lo registran como frontera: la validación de un binding acepta
cualquier orden, pero no lo reordena (@sec:s6.8). Quien construye records
fuera del parser debe usar el orden de la declaración.

Los records también pueden aparecer en reglas, con parámetros dentro. La
inferencia de tipos entra en cada campo y toma su tipo de la declaración. Un
record con campos temporales sigue siendo un término. Sólo se convierte en
tiempo el valor de un campo que se extrae hacia un parámetro `PropositionTime`
(`docs/canonical-typed-substitutions.md`).

## Conjuntos

<!-- covers: 3 -->

`Set T` es el tipo de un conjunto de valores de tipo `T`. En el lenguaje
actual, un conjunto aparece en tres lugares:

- como tipo de un campo de entidad, por ejemplo `assets : Set Thing`;
- en el estado inicial de un experimento, con un literal como
  `state @ tau { juan.assets = {car}, }`;
- en las operaciones `+=` y `-=` del cuerpo de un verbo `effect`.

Los términos de los eventos no tienen literales de conjunto. Un conjunto no
es, por tanto, un argumento ordinario de un evento. Es la forma en que el
estado guarda colecciones. El cierre nunca lee ese estado, y su ejecución
pertenece a otra capa (@sec:s7.4).

La elaboración comprueba los conjuntos en los dos lugares donde aparecen. En
el estado inicial, cada elemento debe ser una constante asignable al tipo del
elemento. En un efecto, el campo de destino debe ser un conjunto (`is not a
set field`), y el valor añadido o retirado debe ser asignable a su tipo de
elemento.

## Opcionales y `none`

<!-- covers: 4 -->

`T?` es el tipo opcional de `T`. Su valor vacío se escribe `none`. Un campo o
un argumento de tipo `T?` admite dos clases de valores:

- `none`;
- un valor de tipo `T`, sin envoltura explícita.

El segundo punto merece atención. No existe un constructor del tipo «algún
valor». Una constante `car : Thing` vale directamente donde se espera un
`Thing?`. Lo contrario no vale: `none` en una posición no opcional es un
error.

`none` tampoco se convierte en otra cosa. No puede ser un tiempo, ni en un
evento ni en un binding. Los documentos de Residuum lo dicen expresamente: la
representación de un binding sigue el tipo del parámetro, y `none` no puede
convertirse en un tiempo.

En la inferencia de tipos de las reglas, un parámetro que aparece en una
posición `T?` y en otra `T` recibe el tipo `T`. Es el tipo más estrecho que
cabe en las dos posiciones. Un parámetro que sólo aparece en posiciones `T?`
conserva el tipo opcional.

Los cuatro tipos de esta sección bastan para el dominio jurídico de los
ejemplos de Residuum. Un `Relation` reúne deudor, cosa, conducta, acreedor y
modo; dos de esos campos son opcionales. Un `Patrimony` guarda tres conjuntos.
@Sec:s4.10 muestra esas declaraciones como documentación del dominio.
