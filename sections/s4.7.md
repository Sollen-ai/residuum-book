Un binding asocia un nombre con un valor. En Residuum los nombres obtienen
valor de cuatro maneras: por declaración, por matching, por una consulta y
por un Program. En ninguna de ellas se reasigna un nombre: una vez ligado,
conserva su valor en esa aplicación. Esta sección describe cada una. Cómo
se sustituye después el valor en el cuerpo de la regla corresponde a
@sec:s5.2.

## Constantes

<!-- covers: 1 -->

Una constante se declara con su tipo y no recibe otro valor:

```text
const juan : Person
const tau : PropositionTime
```

El valor de una constante es la propia constante. No hay inicializador ni
expresión que evaluar. Una constante de entidad es una identidad opaca, y una
constante temporal es un instante (@sec:s4.4). Las constantes son ground:
nunca actúan como binders de una sustitución. Una constante con el mismo
nombre que un parámetro restante sigue siendo constante
(`docs/temporal-constructors-experiment.md`).

## Parámetros de regla ligados por matching

<!-- covers: 2 -->

Un parámetro de regla no tiene valor hasta que la regla se aplica. El cierre
liga los parámetros por matching: compara el antecedente de la regla con los
eventos de Known. El matching sólo liga parámetros del lado de la regla. Las
constantes del patrón se comparan literalmente, también dentro de `after` y
de los records.

Un mismo parámetro puede aparecer en varias posiciones, como argumento y como
tiempo. Todas sus apariciones deben recibir valores compatibles. La
representación del valor depende del tipo del parámetro: un parámetro
`PropositionTime` guarda un tiempo, y los demás guardan un término
(`docs/canonical-typed-substitutions.md`).

La búsqueda residual liga los parámetros de otra manera. Parte del objetivo y
lo unifica con la cabecera de cada regla. Lo que la cabecera no fija queda
pendiente. Si un parámetro del cuerpo sigue pendiente, la búsqueda no prueba
valores del dominio: falla con un error que nombra el parámetro.

La aplicación parcial también liga parámetros, por posición y con constantes
de tipo exacto. Ese mecanismo pertenece a @sec:s5.7.

## Bindings de consulta

<!-- covers: 3 -->

Una consulta con ámbito puede fijar parámetros con `with`:

```text
query residual G @ t
using rules { r }
with { rule r.x = c }
```

Un binding de consulta es una restricción. No es evidencia, no entra en Known
y no cambia las reglas. Exige un ámbito explícito con `using`. Los nombres del
valor se resuelven siempre como constantes del módulo, nunca como parámetros
de una regla o de un Program con el mismo nombre.

@Lst:s4-7-with muestra para qué sirve. La regla `lending` tiene un parámetro
`office` que la cabecera no fija. Sin binding, la consulta fallaría con «rule
`lending` has parameter `office` not determined by the goal». El binding fija
ese parámetro, y la búsqueda puede continuar.

```res {#lst:s4-7-with caption="Un binding with que fija un parámetro" run=query}
module Prestamo

entity Person
entity Thing
entity Office

const ana : Person
const book : Thing
const main : Office
const tau : PropositionTime

seeded verb requests(subject : Person, object : Thing)
seeded verb open(office : Office)
derived verb lent(subject : Person, object : Thing)

rule lending(person, object, office, t) =
    requests(person, object) @ t & open(office) @ t <= lent(person, object) @ t

experiment atMain {
    seeds { requests(ana, book) @ tau, }
    query residual lent(ana, book) @ tau
    using rules { lending }
    with { rule lending.office = main }
}
```
::: explanation
El objetivo `lent(ana, book) @ tau` fija `person`, `object` y `t`. El
parámetro `office` sólo aparece en el antecedente. El binding lo fija en
`main`. Con la petición ya en los seeds, el requisito residual es la apertura
de esa oficina. La salida muestra el ámbito y los bindings que usó la
consulta.
:::

Un binding de regla se refiere a la lambda original de la regla. Si la regla
se usa dentro de un Program, el binding alcanza cada RuleUse que la compila.
Dos reglas distintas nunca comparten un binding porque sus parámetros se
llamen igual (`docs/residual-explicit-bindings-api.md`).

La validación rechaza como error un parámetro desconocido, un tipo incorrecto
y un binding duplicado o inconsistente (@sec:s4.6). También rechaza un binding
que contradice la cabecera, aunque Known ya contenga el objetivo. Un binding
temporal debe estar resuelto. Para dejar pendiente un tiempo, basta con no
escribir su binding.

## Bindings de Program

<!-- covers: 4 -->

Un Program agrupa reglas con parámetros compartidos (@sec:s5.6). Cada `use`
liga parámetros de la regla con valores:

```text
program Chain(object : Thing, t : PropositionTime) {
    use first { local = object, when = t }
    use second { local = object, when = t }
}
```

A la izquierda de cada `=` va un parámetro de la regla. A la derecha puede ir
un parámetro del Program, una constante visible, `none` o un record. El
elaborador comprueba el tipo de cada binding contra la firma de la regla. Un
parámetro de la regla que el `use` no menciona queda local a ese RuleUse
(`docs/minimal-programs.md`).

Una consulta puede fijar además los parámetros compartidos con
`with { program P.x = c }`. El binding se refiere al Program resuelto, quizá
aplicado parcialmente. Sólo admite los parámetros compartidos que quedan
libres.

`docs/minimal-programs.md` clasifica las verificaciones del Program mínimo como IMPLEMENTED + TESTED en los
casos seleccionados. Añade que esas pruebas no constituyen un teorema de
equivalencia general.
