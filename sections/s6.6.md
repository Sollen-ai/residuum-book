Una máquina abstracta describe la evaluación como un estado y una transición.
El estado guarda lo calculado hasta ahora; la transición da un paso más.
Residuum ofrece varias máquinas de este tipo para su cierre. Unas reanudan un
cierre ya calculado cuando llegan hechos nuevos. Otras exponen cada paso de
la evaluación. Esta sección las describe. El cálculo semi-naive en que se
apoyan está en @sec:s6.5.

Todas comparten tres rasgos. Guardan su estado en memoria entre llamadas.
Usan el reloj externo para sellar sólo justificaciones nuevas. Y no tienen
sintaxis `.res`: la referencia del lenguaje las lista como capacidades sólo
desde Rust.

## IncrementalClosure

<!-- covers: 1 -->

`IncrementalClosure` mantiene un cierre bajo un conjunto fijo de reglas. Su
ciclo de vida tiene dos operaciones:

- `new(seeds, rules, clock)` construye la base cerrada con `close`.
- `update(additions, clock)` añade hechos y actualiza la base por evaluación
  semi-naive. No vuelve a llamar a `close`.

El resultado de `update` es un `ClosureDelta`. Su campo `known` contiene sólo
eventos nuevos, incluidas las seeds añadidas. Su campo `derivations` contiene
las justificaciones nuevas, incluso si concluyen un evento ya conocido. Las
justificaciones anteriores conservan su sello. Una adición vacía o duplicada
no genera trabajo ni sellos.

El significado de la actualización es un menor punto fijo sobre eventos fuera
de la base `B = Close_R(S)`:

```text
Φ(D) = (ΔS \ B) ∪ (T_R(B ∪ D) \ B)
Close_R(S ∪ ΔS) = Close_R(S) ∪ μD. Φ(D)
```

La especificación clasifica esta igualdad, la garantía T12, como THEOREM
condicional. Vale con base cerrada, reglas fijas y ejecuciones que se
estabilizan. Sobre esa base, el MODEL RESULT M9 recorrió 8.192
actualizaciones de una familia ground de dos átomos.

La derivada tiene una ley de composición secuencial, también THEOREM
condicional. Añadir `Δ1` y después `Δ2` da lo mismo que añadir ambos, si el
segundo paso parte de la nueva base cerrada. La derivada no es aditiva desde
una misma base. Con la regla `P & ~P <= ~Q`, añadir `P` o `~P` por separado no
deriva nada más. Añadirlos juntos deriva `~Q`.

La auditoría final clasifica `IncrementalClosure` como IMPLEMENTED + LIMITED.
Sus reglas son privadas y fijas. Clasifica como NOT IMPLEMENTED dos
extensiones:

- eliminar hechos o reglas con retractación;
- una API productiva de cambios de reglas.

La auditoría marca también como NOT IMPLEMENTED la incrementalidad de las
asociaciones `Verb.program`. Esa entrada es anterior al evaluador siguiente,
que mantiene adiciones con activaciones.

## IncrementalProgramClosure

<!-- covers: 2 -->

`IncrementalProgramClosure` aplica la misma idea a un módulo con Programs
asociados a verbos (@sec:s5.6). `close_program`, el cierre en la modalidad
activa, se construye con este evaluador.

Su delta, `ProgramClosureDelta`, informa además de las activaciones. Una
activación nueva no sigue el camino del pivote. Se inicializa evaluando sus
reglas contra todo Known. Las activaciones ya inicializadas y las reglas
ordinarias buscan testigos en la frontera, como en @sec:s6.5. El evaluador
comparte con los demás el índice por argumentos y el join en profundidad.

Su documento de integración da un argumento del scheduler y comparaciones
exactas con el evaluador anterior. No lo presenta como una demostración. La
especificación deja abierta la incrementalización general del estado de
activación.

## ForwardSession

<!-- covers: 3 -->

`ForwardSession` expone el cierre paso a paso. `ForwardSession::new(seeds,
rules)` evalúa un conjunto de reglas ordinarias. `ForwardSession::for_module`
incluye las asociaciones de Programs ejecutables. Cada llamada a
`step(clock)` lee una instantánea fija `X` y devuelve:

- `consequences`: el conjunto `T(X)`, con conclusiones ya conocidas;
- `witnesses`: las instancias inmediatas distintas, con pruebas alternativas;
- `added`: la parte de `T(X)` fuera de `X`;
- `known`: la unión de `X` y `T(X)`;
- las nuevas `derivations` selladas, el número de `round` y si está
  `complete`.

La evaluación es síncrona. Una conclusión de una regla no habilita otra regla
en la misma ronda. Un trigger de activación debe estar ya en `X`; un trigger
nuevo activa su Program en la ronda siguiente.

El documento de evaluación por pasos justifica el esquema. Para antecedentes
Horn finitos, el operador `F(X) = S ∪ T(X)` es Scott-continuo. La unión de
sus aproximaciones de Kleene es el menor cierre. La sesión empieza en `S` y
usa la iteración equivalente `X := X ∪ T(X)`.

La CLI ofrece este modo con las opciones `--steps N` y `--trace`. Cada
invocación empieza una sesión nueva. La salida distingue una evaluación
completa de un límite de pasos. Una traza acotada puede acabar antes de
completar el cierre. Un cierre temporal infinito puede tener tantos pasos
finitos como se quiera, sin resultado completo.

## DerivativeSession

<!-- covers: 4 -->

`DerivativeSession` expone, paso a paso, la actualización de una base. Se
obtiene con `IncrementalClosure::begin_stepwise_update(additions)`, a partir
de la base cerrada que el evaluador mantiene en privado. No modifica esa base
ni llama a `update`.

Su primer paso devuelve las adiciones fuera de `B`. Los pasos siguientes
aproximan el punto fijo `Φ` descrito arriba. `DerivativeStep.delta` es
acumulativo y disjunto de `B`. Las derivaciones antiguas de la base se
conservan sin volver a sellarlas.

Estos pasos son de referencia. Emparejan las reglas contra una instantánea
completa en cada paso. No sustituyen la implementación semi-naive de
`update`.

## El filtro de relevancia

<!-- covers: 5 -->

Un match delta necesita un átomo emparejado con un evento de la frontera. El
matcher rechaza todo par con verbo, polaridad o aridad distintos. Por tanto,
una regla cuyos átomos no comparten encabezado con la frontera no tiene
pivote. Puede saltarse sin cambiar ningún resultado.

`RuleHeaders` precalcula, para cada regla, los encabezados de sus átomos. En
cada ronda delta, `relevant(frontier)` marca las reglas con algún encabezado
presente en la frontera. Las reglas se examinan en el orden del módulo, así
que el orden de descubrimiento no cambia. Una regla con sólo `I` nunca es
relevante para un delta.

El filtro se aplica en `IncrementalClosure::update` y en
`IncrementalProgramClosure`, a las reglas ordinarias y a las de Programs
activados. Las inicializaciones completas no se filtran: la ronda inicial y
cada activación nueva examinan todas sus reglas.

El filtro tiene un efecto visible. El contador `rules_examined` cuenta ahora
sólo las reglas relevantes. Depende, por tanto, de los encabezados de la
frontera, además del número de reglas y rondas.

## Una base y su actualización

El runner de fixtures tiene un modo `--incremental`. Lee dos experimentos
llamados `base` y `delta` y compara la actualización con `close` desde cero.
Ese modo pertenece al runner, no a la CLI. @Lst:s6-6-incremental reproduce
la misma comparación con dos cierres completos.

```res {#lst:s6-6-incremental caption="La base y la unión de base y delta" run=run}
module Incremental

entity Person
entity Thing

const alice : Person
const bob : Person
const car : Thing
const tau : PropositionTime

seeded verb agreesPrice(subject : Person, object : Thing, recipient : Person)
seeded verb agreesObject(subject : Person, object : Thing, recipient : Person)
derived verb saleEstablished(subject : Person, object : Thing, recipient : Person)
derived verb deliverable(subject : Person, object : Thing, recipient : Person)

rule sales(debtor, object, creditor, t) =
    agreesPrice(debtor, object, creditor) @ t
    & agreesObject(creditor, object, debtor) @ t
    <= saleEstablished(debtor, object, creditor) @ t

rule consequence(debtor, object, creditor, t) =
    saleEstablished(debtor, object, creditor) @ t
    <= deliverable(debtor, object, creditor) @ t

// La base: sólo el acuerdo de precio.
experiment base {
    seeds { agreesPrice(alice, car, bob) @ tau, }
    query residual deliverable(alice, car, bob) @ tau
}

// La base más el delta: se añade el acuerdo de objeto.
experiment union {
    seeds {
        agreesPrice(alice, car, bob) @ tau,
        agreesObject(bob, car, alice) @ tau,
    }
    query residual deliverable(alice, car, bob) @ tau
}
```
::: explanation
El módulo sigue la fixture `examples/experiments/forward_incremental.res`.
Allí el segundo experimento se llama `delta` y sólo trae el acuerdo de
objeto. Aquí `union` junta las seeds de ambos, porque `run` no actualiza una
base. La diferencia entre los dos Known es el delta lógico. El objetivo pasa
de falso a verdadero.
:::

La base tiene un evento. El cierre de la unión tiene cuatro. El delta lógico
es la diferencia: el acuerdo de objeto, la venta y la entrega. La
documentación del modo `--incremental` informa lo mismo para su fixture: un
evento en la base, tres en el delta y cuatro en ambos cierres finales.

Ese modo tiene límites declarados. Sólo admite Horn sin defaults, cláusulas
residuales ni verbos `effect`. Exige dependencias acíclicas antes de calcular
cualquier cierre, como condición suficiente de terminación. Y sólo mantiene
adiciones bajo reglas fijas.
