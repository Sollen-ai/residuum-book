La semántica denotacional asigna a cada programa un objeto matemático: su
denotación. En la programación lógica, ese objeto es el modelo mínimo del
programa. Van Emden y Kowalski lo caracterizaron como el menor punto fijo de
un operador de consecuencias inmediatas [@vanemden1976semantics]. Residuum
adopta la misma idea para su núcleo Horn. Esta sección define el objeto. Cómo
lo calcula el motor es tema de @sec:s6.5.

## El operador de consecuencias

La especificación del núcleo parte de un conjunto fijo de reglas `R`. Cada
regla es una lambda `λx.(A ≤ C)`: un antecedente `A`, una conclusión `C` y sus
parámetros. Sobre un conjunto de eventos `F`, el operador de consecuencias
explícitas da las conclusiones de todas las instancias cuyo antecedente encaja
en `F`:

```text
T_R(F) = { θC | λx.(A ≤ C) ∈ R,  (θ, w) ∈ Match(F, A),  θC ground }
```

`Match(F, A)` devuelve pares `(θ, w)`. `θ` es una sustitución compatible y `w`
la lista ordenada de eventos usados como testigos. El matcher reconoce tres
formas de antecedente: la unidad `I`, un evento y la conjunción `&`.

`T_R` produce consecuencias inmediatas, pero puede no contener su propia
entrada. La especificación evita esa confusión con un operador extensivo, que
también recibe las seeds `S`:

```text
H_{S,R}(F) = S ∪ F ∪ T_R(F)
```

## El cierre como menor punto fijo

El cierre de `S` bajo `R` tiene dos definiciones equivalentes. La primera es
una iteración por etapas:

```text
F_0 = S,   F_{n+1} = F_n ∪ T_R(F_n),   Close_R(S) = ⋃_{n<ω} F_n
```

La segunda es el menor punto fijo del operador extensivo:

```text
Close_R(S) = μF. H_{S,R}(F)
```

La especificación advierte un detalle de notación. «Close = μT» sólo es
correcto si `T` nombra el operador con seeds y acumulación. No vale para la
función de consecuencias inmediatas `T_R`.

La garantía T5, el cierre Horn mínimo, fija las propiedades del objeto. La
especificación la clasifica como THEOREM con justificación condicional. Con
matching positivo, reutilizable y que respeta el scope, y con reglas fijas de
cuerpo finito:

- `T_R` es monótono;
- `Close_R(S)` es el menor conjunto que contiene `S` y está cerrado bajo `R`;
- `Close_R(S)` es extensivo, monótono e idempotente.

El argumento tiene tres pasos. Los testigos de una instancia siguen
disponibles al añadir evidencia. Todo cierre que contiene `S` contiene cada
etapa `F_n`. Toda prueba finita del límite usa evidencia de alguna etapa
finita. Los conjuntos de eventos ordenados por inclusión forman un retículo
completo (@sec:s6.4). En él, un operador monótono tiene menor punto fijo
[@tarski1955lattice]; los cuerpos finitos hacen que las etapas lo alcancen.

## Un objeto que puede ser infinito

La denotación existe aunque no sea finita. Una regla puede generar los tiempos
`t`, `after(t)`, `after(after(t))` sin fin. El objeto `Close_R(S)` sigue bien
definido como unión de etapas. El motor, en cambio, sólo puede devolverlo en
tiempo finito cuando la iteración se estabiliza. La especificación lo dice
así: la monotonía no implica terminación (@sec:s6.11).

El cierre devuelto por la API tiene además justificaciones y sellos de
derivación. Las ecuaciones anteriores describen sólo su proyección Known. Los
registros de derivación no forman parte de la denotación.

## Del programa al operador

La especificación no asigna a un programa un conjunto de eventos, sino un
operador. Un programa tipado `Π` reúne declaraciones, reglas y asociaciones
opcionales de verbos con reglas. Su interpretación es una función monótona
sobre conocimiento:

```text
O : Program → Mon(K, K),   Π ↦ T_Π
```

La entrada `S` no forma parte del programa. El cierre de `S` se obtiene
después, con la construcción anterior. Así, el mismo programa denota una
familia de modelos mínimos, uno por cada entrada.

Con Programs asociados a verbos, `T_Π` reúne las conclusiones de las reglas
ordinarias y las de las definiciones activadas. Una definición se activa cuando Known contiene una
instancia positiva del verbo (@sec:s5.6). La garantía T6, de clase THEOREM con
las hipótesis de matching de T5, dice que añadir instancias no retira
activaciones. `T_Π` es
monótono y admite el cierre por la misma construcción. El resultado se
escribe `Close_Π(S)`.

## Un cierre pequeño

```res {#lst:s6-3-cierre caption="Un cierre pequeño y su modelo mínimo" run=run}
module Cierre

entity Person
entity Thing

const ana : Person
const bob : Person
const car : Thing
const tau : PropositionTime

seeded verb agreesPrice(subject : Person, object : Thing, recipient : Person)
seeded verb agreesObject(subject : Person, object : Thing, recipient : Person)
seeded verb donates(subject : Person, object : Thing, recipient : Person)
derived verb saleEstablished(subject : Person, object : Thing, recipient : Person)
derived verb deliverable(subject : Person, object : Thing, recipient : Person)
derived verb registryOpen(object : Thing)

// Dos acuerdos implican la venta.
rule sales(debtor, object, creditor, t) =
    agreesPrice(debtor, object, creditor) @ t
    & agreesObject(creditor, object, debtor) @ t
    <= saleEstablished(debtor, object, creditor) @ t

// La venta implica la entrega en el instante siguiente.
rule consequence(debtor, object, creditor, t) =
    saleEstablished(debtor, object, creditor) @ t
    <= deliverable(debtor, object, creditor) @ after t

// Una donación también implica la entrega.
rule gift(donor, object, donee, t) =
    donates(donor, object, donee) @ t <= deliverable(donor, object, donee) @ after t

// Axioma ground: vale sin premisas.
rule registry() = I <= registryOpen(car) @ tau

experiment both {
    seeds {
        agreesPrice(ana, car, bob) @ tau,
        agreesObject(bob, car, ana) @ tau,
    }
    query residual deliverable(ana, car, bob) @ after tau
}
```
::: explanation
El módulo adapta la fixture `examples/experiments/forward_incremental.res`.
Añade una regla de donación y un axioma con `I`. `run` calcula el cierre
hacia delante y muestra Known al terminar. Known contiene las dos seeds, la
venta, la entrega y el axioma. No contiene ninguna donación, porque nada la
fuerza. El campo `query residual` sólo nombra el objetivo; `run` no ejecuta la
consulta residual.
:::

@Lst:s6-3-cierre muestra las tres fuentes de un evento en el cierre. Las
seeds entran por `S`. La venta y la entrega entran por `T_R`, en dos etapas.
El axioma `registry` entra sin premisas, porque la teoría contiene la regla
`I <= registryOpen(car) @ tau`. La unidad `I` no implica cualquier conclusión;
sólo justifica la de ese axioma.

El cierre es mínimo. La regla `gift` está en el programa, pero ningún evento
la activa. Añadir un hecho de donación al cierre daría otro conjunto cerrado
bajo `R`, pero mayor. La denotación es el menor de todos.

## Modelo mínimo y modelos de la teoría

El puente entre teorías y modelos da otra lectura del mismo objeto. Para la
política de soporte Horn, los modelos de `R` son los conjuntos cerrados bajo
sus reglas. Su intersección también es cerrada. El núcleo de literales
comunes a todos los modelos de la teoría coincide con el cierre:

```text
γ_H(S) = Close_R(S)
```

El cierre es, por tanto, el modelo mínimo para esa política. El documento
apoya la igualdad en un argumento condicional y en un MODEL RESULT: 4.016
teorías de una familia de dos átomos, sin discrepancias.

El mismo puente marca el límite de esta denotación. Con la política
FOUR-fusión, el cierre Horn está contenido en el núcleo de literales comunes,
y la inclusión puede ser estricta. En la misma familia, Horn difirió del
mínimo FOUR en 640 teorías. Esa diferencia es objeto de @sec:s6.10. La
semántica operacional elegida sigue siendo el cierre Horn mínimo, no todo
entailment FOUR.
