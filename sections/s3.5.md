Un texto es ambiguo si admite dos árboles sintácticos, o si un mismo nombre
puede referirse a dos cosas. Esta sección responde las dos preguntas para
Formal. Para el parser actual, la respuesta corta es no, en ambos casos. Cada «no» tiene, sin
embargo, una regla concreta detrás.

## Un solo árbol por texto

El parser de chumsky usa `choice`, que prueba sus alternativas en orden y se
queda con la primera que funciona (@sec:s3.4). Esa elección ordenada es la de
las gramáticas de expresiones de análisis (PEG) [@ford2004peg]. Por
construcción, el parser da un solo árbol a cada texto aceptado. Es una
propiedad del parser, no de la gramática: nadie ha probado que la EBNF de
@sec:s3.2 sea no ambigua (@sec:s2.2). Las alternativas de Formal, además, se
separan pronto:

- cada declaración empieza por una palabra clave distinta;
- `rule r(…) = …` define una regla y `rule r = f(…)` la aplica: decide el
  token que sigue al nombre;
- `program` se distingue del mismo modo, por `=` o por `(`;
- en un antecedente se prueba primero un evento, así que `I(x)` es un verbo
  llamado `I` y `I` solo es la condición vacía;
- en un término, `after(` abre el constructor y `after` solo es un nombre.

Tampoco hay precedencia que resolver. El único operador binario de un
antecedente es `&`. Una regla tiene un solo `<=` y, como mucho, un `-o`.

Las palabras clave no están reservadas. `const rule : Thing` es una
declaración válida, y `rule` pasa a ser una constante. El parser no se
confunde, porque cada palabra clave sólo cuenta en su posición. Lo mismo vale
para `after`: con una constante temporal llamada `after`, el texto `@ after`
es un tiempo simple. El lector humano sí puede confundirse. Formal no lo
impide.

## Constantes frente a parámetros

Un mismo identificador puede nombrar una constante del módulo y un parámetro
de una regla. La elaboración, en `src/elab.rs`, resuelve el conflicto según
el lugar donde aparece el nombre:

- **Cuerpo de una regla.** Un parámetro de la cabecera oculta a la constante
  homónima. Si el nombre no es parámetro, debe ser constante. Si no es
  ninguna de las dos cosas, la regla es un error.
- **Cabecera vacía.** `rule r() = …` infiere los parámetros a partir de los
  nombres del cuerpo. Las constantes declaradas quedan fuera: siguen siendo
  ground.
- **Seeds, premises y objetivo.** Todo nombre debe ser una constante.
- **Valor de un binding.** En `with { rule r.x = v }`, el lado izquierdo nombra
  un parámetro de `r`. El valor `v` se resuelve sin ámbito de parámetros: es
  siempre una constante.

La última regla está escrita en `docs/residual-query-source-bindings.md`. Un
parámetro homónimo de la consulta no captura el identificador del valor.
@Lst:s3-5-homonimo lo muestra con un parámetro que la cabeza de la regla no
fija.

```res {#lst:s3-5-homonimo caption="Un binding cuyo valor se llama como el parámetro" run=query}
module Homonimos

entity Person
entity Thing

const ana : Person
const lender : Person
const book : Thing
const tau : PropositionTime

seeded verb requests(subject : Person, object : Thing)
seeded verb owns(owner : Person, object : Thing)
derived verb lent(subject : Person, object : Thing)

// lender es parámetro de la regla y también constante del módulo.
// La cabeza no lo fija: sólo aparece en el antecedente.
rule lending(person, object, lender, t) =
    requests(person, object) @ t & owns(lender, object) @ t
    <= lent(person, object) @ after t

experiment homonym {
    seeds { requests(ana, book) @ tau, }
    query residual lent(ana, book) @ after tau
    using rules { lending }
    with { rule lending.lender = lender }
}
```
::: explanation
Dentro de la regla, `lender` es el parámetro y oculta a la constante. En el
binding, el lado izquierdo nombra ese parámetro. El lado derecho es la
constante `lender`. El requisito que falta menciona esa constante, así que el
binding fijó el parámetro con un valor ground.
:::

La regla de ocultación tiene una consecuencia práctica. Si se borra un
parámetro de la cabecera pero su nombre sigue en el cuerpo, la regla no falla
cuando existe una constante homónima. El nombre pasa a ser esa constante y la
regla cambia de significado sin aviso. Añadir una constante, en cambio, nunca
cambia una regla cuyo parámetro ya tiene ese nombre.

Si el valor capturara el parámetro, el binding diría `lender = lender` y no
fijaría nada. La búsqueda informaría entonces del parámetro pendiente, en
lugar de dar un requisito (@sec:s6.8).

## Binders homónimos

Dos reglas pueden usar los mismos nombres de parámetro. Cada regla es su
propio binder, así que el `t` de una no es el `t` de otra. Un binding no
puede mezclarlas: su forma `rule r.x` nombra la regla además del parámetro. Un
binding de Program, `program P.x`, nombra del mismo modo su Program. @Sec:s4.8
trata el ámbito y la higiene en general.
