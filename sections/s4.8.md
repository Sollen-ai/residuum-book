El ámbito de un nombre es la parte del programa donde ese nombre es visible.
En un lenguaje con ámbito léxico, el ámbito se decide leyendo el texto, sin
ejecutar nada. Residuum tiene tres niveles de ámbito: el módulo, la regla y
el Program. Además impide que dos nombres iguales se confundan al compilar un
Program. Esta sección recorre los tres niveles y termina con los imports.

## Ámbito de módulo

<!-- covers: 1 -->

Todas las declaraciones de un módulo comparten un solo espacio de nombres.
Una entidad, una regla y un Program no pueden llamarse igual. Un
nombre repetido es un error del resolver (`duplicate symbol`). No hay
espacios de nombres separados para tipos y valores.

La visibilidad sigue el orden del texto. El elaborador lee el módulo de
arriba abajo y cada regla ve lo declarado antes que ella. Un `use` dentro de
un Program también exige que la regla ya esté elaborada o importada. Hay dos
excepciones:

- un campo de record puede nombrar una entidad declarada más abajo;
- la asociación `= program P` de un verbo se resuelve al final.

## Parámetros locales a la regla

<!-- covers: 2 -->

Los parámetros de una regla sólo son visibles en su cuerpo. Dos reglas pueden
usar el mismo nombre de parámetro sin relación alguna. Una restricción sobre
el `person` de una regla no afecta al `person` de otra.

Un parámetro tapa a una constante con el mismo nombre. El elaborador busca
primero entre los parámetros y luego entre las constantes. La fixture
`temporal_identity_formal.res` declara una constante `t` y una regla con un
parámetro `t`; dentro de la regla, `t` es el parámetro (@sec:s4.4). Una
cabecera vacía, en cambio, nunca convierte una constante en parámetro.

Los bindings de consulta no abren un ámbito nuevo. Los nombres de sus valores
se resuelven sólo como constantes del módulo (@sec:s4.7).

## Nombres higiénicos de los parámetros de Program

<!-- covers: 3 -->

Un Program se compila a reglas ordinarias, una por cada `use`
(`compile_program` en `src/programs.rs`). Cada regla compilada recibe un
nombre propio, `Programa::índice::regla`. El índice distingue dos usos de la
misma regla.

Los parámetros también se renombran. Un parámetro compartido `x` del Program
`P` pasa a llamarse `#P:shared:x`. Un parámetro de la regla que el `use` no
liga pasa a llamarse `#P:useN:x`, con el índice del uso. El código fuente no
puede escribir estos nombres, según el propio código. Así ningún nombre del
usuario puede capturarlos.

Esta higiene tiene tres efectos:

- un parámetro compartido es el mismo binder en todos los usos;
- un parámetro local de un uso es independiente del de otro uso;
- una constante capturada sigue siendo constante, y no se liga nada por
  coincidencia de nombre (`docs/minimal-programs.md`).

@Lst:s4-8-usos lo muestra con dos usos de una misma regla.

```res {#lst:s4-8-usos caption="Dos RuleUses de una regla con parámetros independientes" run=query}
module Usos

entity Person
const ana : Person
const bob : Person
const tau : PropositionTime

seeded verb notified(person : Person)
derived verb served(person : Person)
derived verb linked(a : Person, b : Person)

rule service(person, t) = notified(person) @ t <= served(person) @ t
rule link(a, b, t) = served(a) @ t & served(b) @ t <= linked(a, b) @ t

program Both(a : Person, b : Person, t : PropositionTime) {
    use service { person = a, t = t }
    use service { person = b, t = t }
    use link { a = a, b = b, t = t }
}

experiment twoUses {
    premises { notified(ana) @ tau, notified(bob) @ tau, }
    query fourFusion linked(ana, bob) @ tau
    using program Both
    with { program Both.a = ana, program Both.b = bob, program Both.t = tau }
}

experiment oneRule {
    premises { notified(ana) @ tau, notified(bob) @ tau, }
    query fourFusion linked(ana, bob) @ tau
    using rules { service, link }
    with { rule service.person = ana, rule service.t = tau, rule link.a = ana, rule link.b = bob, rule link.t = tau }
}
```
::: explanation
En `twoUses`, los dos usos de `service` compilan a dos reglas. Cada una liga
su `person` a un parámetro compartido distinto, así que se sirve a `ana` y a
`bob`. En `oneRule`, la regla `service` aparece una sola vez en el ámbito. Su
binding fija `person` en `ana`, y `served(bob)` no se obtiene. Se usa
`fourFusion` porque instancia cada regla del ámbito con sus bindings, y así
se ve cuántas instancias hay.
:::

@Lst:s4-8-usos usa una consulta `fourFusion` (@sec:s6.10). Esa consulta
instancia cada regla del ámbito con sus bindings. Un binding `rule r.x = c`
fija el mismo valor en todos los usos de `r`. Para dos instancias de una
regla hace falta un Program, porque cada uso compila a su propia regla
(`docs/executable-fixtures.md`).

## Imports

<!-- covers: 4 -->

Un fichero importa las declaraciones de otro con una ruta relativa:

```text
import "./ontology_reference/legal_general.res"
```

El resolver (`src/modules.rs`) aplica estas reglas:

- **Qué se importa.** Todas las declaraciones salvo los experimentos. También
  las dependencias transitivas: en este primer sistema de módulos, todo
  símbolo es público.
- **Ámbito propio.** Cada dependencia se elabora en su propio ámbito, antes
  que el módulo que la importa. Un módulo nunca ve símbolos de un módulo
  hermano ni del consumidor.
- **Colisiones.** Dos declaraciones con el mismo nombre y distinto origen son
  un error. Importar dos veces el mismo fichero, también en diamante, no lo
  es.
- **Ciclos.** Un import circular es un error (`cyclic import`).
- **Límites.** El grafo admite hasta 64 ficheros únicos y 1 MiB de fuente.

Un Program conserva el ámbito léxico del módulo que lo define. Si otro módulo
lo aplica parcialmente, el resultado sigue usando las reglas del módulo de
definición. No se buscan símbolos nuevos en el consumidor.

No hay imports selectivos, alias ni símbolos privados. Toda colisión de
nombres entre módulos se resuelve renombrando en el código fuente.
