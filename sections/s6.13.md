Esta sección sigue un módulo pequeño desde el texto hasta la respuesta. No
introduce conceptos nuevos: aplica los de las Partes 3 a 6. En cada etapa
muestra la forma intermedia que la herramienta deja ver. Cuando una etapa no
tiene forma imprimible en el commit fijado, la sección lo dice y muestra el
código que la ejecuta.

El recorrido sigue el pipeline activo que describe la referencia del
lenguaje. El texto Formal pasa a un SurfaceAST y después a un TypedAST. Sobre
este último trabajan la derivación y las consultas. @Sec:s1.4
presenta ese pipeline en general. Aquí se ve sobre un caso concreto.

## El módulo

El módulo describe una venta. Si el vendedor acepta y el comprador paga, el
vendedor debe entregar en el instante siguiente. Los verbos `seeded` son los
hechos de entrada: el acuerdo y el pago. El verbo `derived` es la conclusión:
la deuda. La conclusión vive en `after t`, un instante después de sus
antecedentes (@sec:s4.4).

```res {#lst:s6-13-modulo caption="El módulo trazado" run=run}
module Deuda

entity Person
entity Thing

const ana : Person
const bob : Person
const car : Thing
const tau : PropositionTime

seeded verb agrees(seller : Person, object : Thing, buyer : Person)
seeded verb pays(buyer : Person, object : Thing, seller : Person)
derived verb owes(seller : Person, object : Thing, buyer : Person)

// El acuerdo y el pago implican la deuda de entrega en el instante siguiente.
rule sale(seller, object, buyer, t) =
    agrees(seller, object, buyer) @ t & pays(buyer, object, seller) @ t
    <= owes(seller, object, buyer) @ after t

experiment complete {
    seeds { agrees(ana, car, bob) @ tau, pays(bob, car, ana) @ tau, }
    query residual owes(ana, car, bob) @ after tau
}

experiment paidOnly {
    seeds { pays(bob, car, ana) @ tau, }
    query residual owes(ana, car, bob) @ after tau
}
```
::: explanation
El módulo tiene dos verbos `seeded`, un verbo `derived` y una regla de Horn.
La regla se lee «el acuerdo y el pago implican la deuda». Los dos experimentos
difieren en una seed: `paidOnly` no tiene el acuerdo. `run` calcula el cierre
de cada experimento y no ejecuta la consulta declarada.
:::

@Lst:s6-13-modulo se ejecuta con `run`. Su salida es la del cierre, la tercera
etapa. Antes hay dos etapas que no imprimen nada.

## Análisis sintáctico

La primera etapa lee el texto y produce un SurfaceAST (@sec:s3.4). La línea de
órdenes no imprime ese árbol. El cargador de módulos llama al parser así:

```rust {#lst:s6-13-parser caption="La llamada al parser en el cargador de módulos" run=include include=residuum@d4d2282:src/modules.rs#L71-L76}
```
::: explanation
El cargador lee el fichero y llama a `parse_formal`. Un fallo se devuelve con
la ruta del fichero delante. Si el análisis tiene éxito, `resolve` resuelve
los imports y elabora el resultado.
:::

Sólo el fallo deja una huella visible. Si falta una coma entre dos seeds, el
parser se detiene:

```res {#lst:s6-13-sintaxis caption="Un error de análisis sintáctico" run=expect-error cmd=run setup=s6-13-deuda}
experiment missingComma {
    seeds { agrees(ana, car, bob) @ tau pays(bob, car, ana) @ tau, }
    query residual owes(ana, car, bob) @ after tau
}
```
::: explanation
El setup oculto contiene las declaraciones y la regla de @lst:s6-13-modulo.
Dentro de `seeds`, las comas entre eventos son obligatorias. El mensaje nombra
lo que el parser esperaba, una coma o una llave de cierre, y lo que encontró.
:::

El mensaje reproduce el error del parser sin traducirlo. Lleva delante el
nombre del fichero y la marca `formal parse error`. Después da el conjunto de
símbolos esperados, `Comma` y `RBrace`, y el símbolo encontrado, el
identificador `pays`. El módulo no llega a ninguna etapa posterior.

## Elaboración

La segunda etapa convierte el SurfaceAST en un TypedAST (@sec:s4.1). Resuelve
nombres, comprueba tipos y lleva las reglas a su forma interna. Tampoco hay
una orden que imprima el TypedAST. El cargador lo produce aquí:

```rust {#lst:s6-13-elaborador caption="La llamada al elaborador en el cargador de módulos" run=include include=residuum@d4d2282:src/modules.rs#L124-L132}
```
::: explanation
Antes de elaborar, `validate_types` comprueba que cada entidad nombrada en un
tipo esté declarada, en el módulo o en sus imports. Después,
`elaborate_formal_with_dependencies` produce el módulo tipado. Sus errores también llevan delante la ruta del
fichero.
:::

En la regla `sale`, los parámetros no llevan tipo. El elaborador los infiere
de los verbos donde aparecen: `seller` es un `Person` porque ocupa el primer
lugar de `agrees`. Lo mismo ocurre con los eventos de los experimentos, que se
comprueban contra la firma de su verbo. Una seed con un argumento del tipo
equivocado no pasa de esta etapa:

```res {#lst:s6-13-tipos caption="Un error de elaboración" run=expect-error cmd=run setup=s6-13-deuda}
experiment wrongType {
    seeds { agrees(car, ana, bob) @ tau, }
    query residual owes(ana, car, bob) @ after tau
}
```
::: explanation
El primer parámetro de `agrees` es un `Person`, y `car` es un `Thing`. El
texto es sintácticamente correcto, así que el parser lo acepta. El elaborador
lo rechaza, porque `Thing` no es asignable a `Person` (@sec:s4.3).
:::

Hay una huella de la elaboración en las salidas correctas. El texto escribe el
objetivo con `@ after tau`, y la salida de @lst:s6-13-modulo lo imprime como
`after(tau)`. La salida muestra el tiempo ya elaborado, no el texto fuente.

## Cierre

Cada orden lleva el módulo tipado a un runner distinto:

```rust {#lst:s6-13-ordenes caption="Cada orden de la CLI y su runner" run=include include=residuum@d4d2282:src/bin/residuum/cli.rs#L72-L78}
```
::: explanation
`run` y `explain` usan el runner hacia delante. `query` usa el runner de
experimentos, que ejecuta la consulta declarada. La orden `explain` sólo
cambia la presentación del mismo cierre.
:::

El listado muestra sólo el reparto final. Antes, la misma función comprueba si
el módulo tiene defaults. En ese caso, toda orden salvo `query` usa en su lugar
el runner de defaults (@sec:s6.9). Este módulo no tiene ninguno.

La salida de @lst:s6-13-modulo es el cierre de cada experimento:

- **`complete`.** Known contiene las dos seeds y la deuda
  `owes(ana, car, bob) @ after(tau)`. La línea `Horn` vale `true`.
- **`paidOnly`.** Known sólo contiene el pago. La regla no se aplica y `Horn`
  vale `false`.

Cada bloque repite primero la entrada (`Seeds`) y el objetivo (`goal`). La
línea `Horn` dice si el objetivo está en el cierre. La línea
`Known after close` da el cierre entero. Las seeds siguen en él: el cierre es
extensivo.

El runner hacia delante sólo acepta experimentos con `seeds`. Un experimento con
`premises` lo rechaza (`src/experiments.rs`). Las premisas son hipótesis
lógicas de una comparación, no hechos de entrada (@sec:s6.10). Por eso la consulta FOUR del final usa un
listado aparte, con la orden `query`.

El cierre es el modelo mínimo de @sec:s6.3. Para ver por qué se derivó la
deuda, `explain` muestra la justificación:

```res {#lst:s6-13-justificacion caption="La justificación de la deuda" run=explain setup=s6-13-deuda}
experiment complete {
    seeds { agrees(ana, car, bob) @ tau, pays(bob, car, ana) @ tau, }
    query residual owes(ana, car, bob) @ after tau
}
```
::: explanation
El listado repite el experimento `complete`. La salida numera los eventos de la
prueba. La deuda lleva la regla `sale`, su sello `derivedAt`, la sustitución
de los cuatro parámetros y las referencias a sus dos antecedentes. Las dos
seeds no tienen regla: son hechos de entrada.
:::

La salida de `explain` no expande la prueba como un árbol. Numera cada evento
una vez y lo cita por su número. Así conserva todas las justificaciones sin
duplicar ramas compartidas. La línea `verb origin` da el módulo y el fichero
del verbo. La línea `seed` marca los hechos de entrada.

La sustitución de @lst:s6-13-justificacion es el paso de parámetros de
@sec:s5.2. Fija `seller`, `object`, `buyer` y `t`. El sello `derivedAt` es
operacional: registra cuándo se derivó el evento.

## Consulta residual

En `paidOnly` el cierre no llega a la deuda. La consulta residual pregunta qué
falta (@sec:s6.8):

```res {#lst:s6-13-residual caption="Lo que falta para la deuda" run=query setup=s6-13-deuda}
experiment nothing {
    seeds {}
    query residual owes(ana, car, bob) @ after tau
}

experiment paidOnly {
    seeds { pays(bob, car, ana) @ tau, }
    query residual owes(ana, car, bob) @ after tau
}
```
::: explanation
`query` ejecuta ahora la consulta declarada. Sin seeds, el requisito es el
producto del acuerdo y el pago. Con el pago, el requisito es sólo el acuerdo.
La línea `Known after close` sigue mostrando el cierre real, sin hipótesis.
:::

En `nothing`, los dos antecedentes faltan. El requisito es su producto `⊗`:
ambos pertenecen a la misma rama de explicación. No hay `∨`, porque una sola
regla concluye la deuda. En `paidOnly`, la búsqueda sigue estos pasos.

La búsqueda va hacia atrás desde el objetivo. Unifica la cabeza de `sale` con
`owes(ana, car, bob) @ after(tau)` y obtiene la sustitución. Después examina
los dos antecedentes:

1. `pays(bob, car, ana) @ tau` está en la evidencia de `paidOnly` y aporta `I`.
2. `agrees(ana, car, bob) @ tau` es un seed ausente y abducible: se propone
   como hipótesis.

El producto de `I` y la hipótesis es la hipótesis. El replay vuelve a aplicar
hacia delante cada paso de la prueba y comprueba que concluye la deuda. La hipótesis nunca entra en
Known: la línea `Known after close` de `paidOnly` sigue sin el acuerdo.

## Consulta FOUR

La última etapa lee la regla como desigualdad en FOUR (@sec:s6.10). Supongamos
que hubo pago y que no hay deuda. ¿Se sigue que no hubo acuerdo?

```res {#lst:s6-13-four caption="La regla leída hacia atrás en FOUR" run=query setup=s6-13-deuda}
experiment noDebt {
    premises { pays(bob, car, ana) @ tau, ~owes(ana, car, bob) @ after tau, }
    query fourFusion ~agrees(ana, car, bob) @ tau
    using rules { sale }
    with {
        rule sale.seller = ana,
        rule sale.object = car,
        rule sale.buyer = bob,
        rule sale.t = tau
    }
}
```
::: explanation
La regla `sale` tiene parámetros, así que la consulta la instancia con un
ámbito y cuatro bindings. Las premisas dan el pago y la evidencia contra la
deuda. El cierre Horn no deriva `~agrees`. FOUR sí, y la respuesta lleva la
marca `explicit scope`.
:::

La instancia ground de `sale` menciona tres átomos: el acuerdo, el pago y la
deuda. Con tres átomos, la consulta enumera las 64 interpretaciones y calcula
también el modelo mínimo. El programa compilado tiene cinco cláusulas:

- las dos premisas;
- el paso hacia delante, del acuerdo y el pago a la deuda;
- dos rotaciones, una por factor del producto.

La rotación del acuerdo dice: si la deuda tiene evidencia en contra y el pago
tiene soporte, el acuerdo tiene evidencia en contra. Las premisas activan esa
cláusula, y el objetivo vale `T` en el modelo mínimo. La enumeración coincide:
el objetivo vale en los cinco modelos que encuentra. La línea `Horn` vale
`false`, porque el paso hacia delante necesita el acuerdo y no lo tiene. La conclusión no entra en
Known: la línea `Known after close` sólo contiene las premisas.
