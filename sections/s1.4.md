Un fichero `.res` recorre varias etapas antes de producir una respuesta. El
pipeline activo es Formal → SurfaceAST → TypedAST → derivación/runtime. Cada
etapa vive en un módulo Rust propio y puede rechazar el fichero con un mensaje
propio. Esta sección sigue un módulo pequeño de principio a fin. Después
muestra un rechazo real de cada etapa.

## El recorrido completo

<!-- covers: 1 -->

@Lst:s1-4-traza es el módulo que seguiremos. Declara una regla con dos
condiciones y pregunta qué falta para un préstamo.

```res {#lst:s1-4-traza caption="Un módulo que recorre todo el pipeline" run=query}
module Biblioteca

entity Person
entity Thing

const ana : Person
const book : Thing
const tau : PropositionTime

seeded verb requests(subject : Person, object : Thing)
seeded verb available(object : Thing)
derived verb lent(subject : Person, object : Thing)

rule lending(person, object, t) =
    requests(person, object) @ t & available(object) @ t <= lent(person, object) @ t

experiment onlyRequest {
    seeds { requests(ana, book) @ tau, }
    query residual lent(ana, book) @ tau
}
```
::: explanation
El experimento aporta la petición, pero no la disponibilidad del libro. La
orden `query` calcula el cierre de los seeds y ejecuta la consulta residual
declarada. La salida dice que el objetivo no está en el cierre Horn. Da además
el requisito residual que falta: `available(book) @ tau`.
:::

La orden `./residuum query biblioteca.res` atraviesa estas etapas:

1. **Carga de módulos** (`modules.rs`). La función `load_formal_module`
   resuelve la ruta canónica del fichero y lee su texto. Después resuelve los
   imports, con rutas relativas al fichero que los declara. Cada dependencia
   se analiza y se elabora por separado; el consumidor recibe declaraciones
   ya tipadas, nunca texto concatenado.
2. **Análisis sintáctico** (`formal.rs`). La función `parse_formal` divide el
   texto en tokens y construye un `FormalModule`. Ese árbol, definido en
   `surface.rs`, es el SurfaceAST. Conserva la forma del texto, todavía sin
   tipos: declaraciones, reglas, experimentos y consultas tal como se
   escribieron.
3. **Elaboración** (`elab.rs`). La elaboración convierte el SurfaceAST en un
   `Module` de `typed.rs`, el TypedAST. Desde un fichero, el cargador llama a
   `elaborate_formal_with_dependencies` con las declaraciones importadas; la
   API de texto usa `elaborate_formal`. La elaboración comprueba cada
   argumento contra la firma de su verbo. Infiere los tipos de los parámetros
   de cada regla a partir de los verbos. Baja también los seeds, las premises
   y las consultas de cada experimento.
4. **Derivación y consultas** (`experiments.rs`, `derive.rs`, `residual/`).
   Para `query`, la función `run_experiments` recorre los experimentos del
   módulo. Para una consulta residual llama a `query_program_residual`, en
   `residual/`, y calcula además el cierre con `close`, en `derive.rs`. Para
   `run`, `explain` y `execute`, la función `run_forward_experiments` calcula
   el cierre con `close_program`, que también activa los Programs asociados a
   verbos.
5. **Ejecución de efectos** (`runtime.rs`). Sólo con `execute`, la función
   `execute_effect` aplica los efectos derivados al estado declarado en el
   experimento (@sec:s7.4).

La carga de módulos tiene sus propios controles. Un ciclo de imports, una ruta
absoluta o un símbolo duplicado son errores. El grafo admite hasta 64 ficheros
únicos y 1 MiB de fuente en total. Un fichero importado por dos dependencias se
carga una sola vez, porque su identidad es su ruta canónica. Los experimentos
de una dependencia nunca se importan.

Dos desvíos dependen del contenido del módulo. Con `run`, `explain` y
`execute`, un módulo con defaults pasa por `run_default_experiments`, que
evalúa primero la selección (@sec:s6.9). La orden `query`, en cambio, rechaza
esos módulos. Una consulta `fourFusion` sigue también otro camino: la decide
el evaluador FOUR de `experiments.rs` (@sec:s6.10).

Con `--steps N` o `--trace`, la CLI cambia sólo la última etapa. La carga, el
análisis y la elaboración no cambian. En lugar de evaluar de una vez, la
CLI avanza por transiciones síncronas y muestra el progreso. Una traza
acotada distingue siempre un cierre completo de un prefijo incompleto. La
orden `execute` no admite estas opciones (@sec:s6.6).

Al final, la CLI escribe el resultado en la salida estándar. Las órdenes
`run`, `explain` y `query` ignoran el estado declarado. La orden `execute`
construye un estado nuevo y no modifica el de entrada.

La salida de @lst:s1-4-traza deja ver la última etapa. La línea de los seeds
y la del objetivo repiten la entrada ya elaborada. La línea `Horn` y la del
cierre vienen de `close`: el objetivo no pertenece a Known. La línea del
requisito viene de la consulta residual. El requisito no se añade a Known; la
consulta sólo lo propone como hipótesis (@sec:s6.8).

Las etapas no se mezclan. El analizador no conoce tipos. El elaborador no
calcula cierres. El motor de derivación recibe reglas ya tipadas y nunca ve
texto. @sec:s3.4 describe el analizador; @sec:p4 trata la elaboración y los
tipos; @sec:s6.5 explica el algoritmo del cierre.

## El punto de entrada: launcher y runner

<!-- covers: 2 -->

El usuario no llama al binario Rust. Llama al launcher `residuum`, un guion
Python en la raíz del repositorio. El launcher acepta cuatro órdenes: `run`,
`query`, `explain` y `execute`. Admite además `--steps N`, con N entre 1 y
4096, y `--trace`. Si la línea de órdenes no tiene esa forma, muestra el uso y
termina. Si la tiene, resuelve la ruta del fichero desde la carpeta del
usuario. Después cede el control al runner acotado, `scripts/test_safe.py`,
con las opciones `--cli` y `--fixture`.

El runner rechaza un fichero raíz de más de 64 KiB. Después hace dos cosas,
cada una dentro de un cgroup de systemd propio:

- compila el binario `residuum`, con un solo trabajo de Cargo;
- ejecuta ese binario sobre el fichero, con su propio tiempo máximo.

Ambos pasos tienen límites de memoria, swap y tiempo. Si el runner no puede
imponerlos, no compila ni ejecuta nada. Si un paso los alcanza, el runner lo
detiene. @sec:s7.2 da las cifras y explica cada control.

El binario repite la comprobación. En `src/bin/residuum.rs`, la función
`require_limits` lee el cgroup del proceso. Si el límite de memoria no es el
del runner, o si hay swap, el binario se niega a ejecutar con el mensaje
`refusing unbounded execution; use the repository's residuum launcher`. Así,
lanzar el binario a mano no evita los límites. Sólo después lee el fichero y
pasa el trabajo a la CLI.

Los errores siguen el mismo camino en todas las etapas. La función `main` del
binario escribe `residuum:` y el mensaje en la salida de errores. Termina con
un código de salida distinto de cero. Los errores de análisis y de
elaboración llevan además la ruta del fichero que los produjo.

## Un rechazo por etapa

<!-- covers: 3 -->

Los tres listados siguientes comparten un setup oculto. El setup declara el
módulo `Biblioteca` de @lst:s1-4-traza, con sus verbos y su regla, pero sin
experimentos. Cada listado añade sólo un experimento defectuoso.

El primer rechazo ocurre en el análisis sintáctico. El texto no tiene la forma
de una declaración Formal, así que no llega a existir un SurfaceAST.

```res {#lst:s1-4-sintaxis caption="Un rechazo del análisis sintáctico" run=expect-error setup=s1-4-base}
experiment broken {
    seeds { requests(ana, book) @ tau, }
    query residual lent(ana, book) tau
}
```
::: explanation
A la consulta le falta el `@` que separa el evento de su tiempo. El analizador
de `formal.rs` no puede construir el experimento y rechaza el fichero entero.
El mensaje empieza por `formal parse error` y nombra el token inesperado. El
error ocurre antes de comprobar ningún tipo.
:::

El segundo rechazo ocurre en la elaboración. El texto es sintácticamente
correcto, pero un argumento tiene el tipo equivocado.

```res {#lst:s1-4-elaboracion caption="Un rechazo de la elaboración" run=expect-error setup=s1-4-base}
experiment swapped {
    seeds { requests(book, ana) @ tau, }
    query residual lent(ana, book) @ tau
}
```
::: explanation
El seed invierte los argumentos de `requests`: pone una `Thing` donde el verbo
espera una `Person`. El analizador acepta el texto, porque la forma es válida.
El elaborador de `elab.rs` compara cada argumento con la firma del verbo y
rechaza el módulo antes de derivar nada.
:::

El tercer rechazo ocurre en la evaluación. El módulo se analiza y se elabora
sin error. La orden pedida, en cambio, no admite su entrada.

```res {#lst:s1-4-evaluacion caption="Un rechazo de la evaluación" run=expect-error setup=s1-4-base}
experiment hypothetical {
    premises { requests(ana, book) @ tau, }
    query fourFusion lent(ana, book) @ tau
}
```
::: explanation
El experimento usa `premises`, hipótesis lógicas, en lugar de `seeds`. La
elaboración acepta esa entrada, porque la consulta `fourFusion` la exige. La
orden `run`, en cambio, calcula un cierre hacia delante y sólo admite seeds.
La función `run_forward_experiments`, en `experiments.rs`, rechaza el
experimento. Con `query`, el mismo módulo sí se evaluaría.
:::

Los tres mensajes señalan etapas distintas. El primero describe tokens; el
segundo, tipos; el tercero, la relación entre una orden y su entrada. Ningún
rechazo produce un resultado parcial: el fichero se acepta entero o no se
ejecuta. Hay más rechazos en cada etapa, como un import cíclico en la carga
de módulos. @sec:s7.5 los reúne.
