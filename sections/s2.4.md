La modularidad mide cómo se divide un programa grande en partes y cómo se
reutilizan esas partes. Una parte modular tiene un nombre, un límite y una
forma de uso. Se puede escribir y comprobar por separado. Otro programa puede
usarla sin copiar su texto.

El criterio examina tres preguntas. La primera es cómo se reparten las
declaraciones entre ficheros. La segunda es cómo se empaqueta un
comportamiento para usarlo varias veces con datos distintos. La tercera es
qué oculta cada parte a quien la usa. Un lenguaje con buena modularidad
responde a las tres con construcciones propias, no con disciplina del
programador.

## El criterio en Residuum

<!-- covers: 1 -->

### Módulos e imports

Cada fichero `.res` empieza con `module Nombre`. Un fichero importa otro con
una ruta relativa a sí mismo: `import "./sales.res"`. El resolver de módulos
tiene estas reglas:

- Importa todas las declaraciones salvo los experimentos.
- Las dependencias transitivas también quedan visibles.
- Un ciclo de imports, una ruta absoluta o una ruta vacía son errores.
- Un símbolo con dos orígenes distintos es un error. El mismo fichero
  importado por dos caminos, en diamante, no lo es.
- El grafo admite hasta 64 ficheros únicos y 1 MiB de fuente en total.

@Lst:s2-4-import muestra un consumidor que importa una biblioteca y la usa
sin copiarla.

```res {#lst:s2-4-import caption="Un módulo que importa un Program y lo especializa" run=include include=residuum@d4d2282:examples/experiments/multi_rule_program_consumer.res}
```
::: explanation
El consumidor importa `associated_multi_rule_program.res`. Asocia su propio
verbo al Program importado `Chain` y especializa `Partial` con `tau`. Ningún
cuerpo de regla se copia. Los experimentos del fichero importado no se
ejecutan en el consumidor.
:::

Cada declaración guarda su origen: el módulo y el fichero que la declaran.
`explain` muestra ese origen junto a cada verbo y cada regla. El ámbito de un
Program es el de su módulo de definición. Un Program importado no busca
símbolos nuevos en el consumidor, ni siquiera cuando el consumidor lo
especializa.

Los imports llegaron después de los primeros experimentos de reutilización.
El de `owns` no los tenía: un harness concatenaba dos ficheros en un solo
espacio de nombres. El resolver actual sustituye esa composición por imports
comprobados.

El sistema de módulos no oculta nada. El código del resolver lo dice: todos
los símbolos que no son experimentos son públicos en este primer sistema. No
hay listas de exportación, espacios de nombres ni nombres cualificados. Dos
bibliotecas que declaran el mismo nombre no pueden importarse juntas.

### Programs y RuleUses

Un Program agrupa reglas con parámetros compartidos (@sec:s5.6). Cada
`use` es un RuleUse: nombra una regla y le da bindings. El elaborador
comprueba el tipo de cada binding contra la firma de la regla. Rechaza
reglas o parámetros inexistentes, bindings duplicados y tipos
incompatibles. Un Program no copia el cuerpo de sus reglas, así que un cambio
en una regla llega a todos los Programs que la usan.

Un Program necesita al menos un `use`, y declararlo no ejecuta nada. Una
misma regla puede aparecer en varios RuleUses del mismo Program. Cada uso
se compila a una regla propia, con un identificador que incluye su posición.
Así, la provenance distingue los usos repetidos. Un verbo también puede
asociarse a un Program, que se activa con cada evento positivo del verbo
(@sec:s5.6).

<!-- covers: 3 -->

### La aplicación parcial como reutilización

Una regla o un Program se especializa fijando sus primeros parámetros con
constantes: `program AnaCase = Case(ana)` (@sec:s5.7). La especialización
crea una declaración nueva sin repetir el cuerpo. El experimento con `owns`
muestra el coste de este diseño. Para escribir `ownsProgram(charlie, molest)`,
la biblioteca tuvo que poner primero los parámetros que se aplican. Con el
orden del primer bosquejo, esa aplicación por prefijo no era posible. El
autor de una biblioteca debe prever qué parámetros fijará el consumidor.

### Ámbitos explícitos de consulta

Una consulta puede limitarse a un Program o a una lista de reglas con
`using`, y fijar parámetros con `with` (@sec:s6.8). @Lst:s2-4-programa
reutiliza un mismo Program con dos bindings y con una especialización.

```res {#lst:s2-4-programa caption="Un Program reutilizado con dos bindings" run=query}
module Expedientes

entity Person

const ana : Person
const bob : Person
const tau : PropositionTime

seeded verb notified(person : Person)
seeded verb paid(person : Person)
derived verb served(person : Person)
derived verb closed(person : Person)

rule service(person, t) = notified(person) @ t <= served(person) @ t
rule closing(person, t) =
    served(person) @ t & paid(person) @ t <= closed(person) @ after t

// Un Program reúne las dos reglas con parámetros compartidos.
program Case(person : Person, t : PropositionTime) {
    use service { person = person, t = t }
    use closing { person = person, t = t }
}

// Aplicación parcial: fija el primer parámetro.
program AnaCase = Case(ana)

experiment forAna {
    seeds { notified(ana) @ tau, }
    query residual closed(ana) @ after tau
    using program Case
    with { program Case.person = ana }
}

experiment forBob {
    seeds { notified(bob) @ tau, paid(bob) @ tau, }
    query residual closed(bob) @ after tau
    using program Case
    with { program Case.person = bob }
}

experiment partial {
    seeds { notified(ana) @ tau, }
    query residual closed(ana) @ after tau
    using program AnaCase
    with { program AnaCase.t = tau }
}
```
::: explanation
`Case` une dos reglas por sus parámetros compartidos. Los dos primeros
experimentos usan el mismo Program con bindings distintos. Para `ana` falta
el pago; para `bob` no falta nada. El tercero usa la especialización
`AnaCase`, que ya fija la persona. Su único binding fija el tiempo, y el
requisito coincide con el de `forAna`.
:::

Un módulo con Programs exige que cada consulta declare su ámbito o sea una
consulta residual activa. La regla evita tratar los miembros de un Program
como reglas ordinarias sin avisar.

El ámbito tiene un límite práctico. Un binding de Program vale para todos sus
usos. Si en algún uso del ámbito el binding es incompatible con el objetivo,
la consulta falla con un error de inconsistencia. No salta ese uso. Un Program
pensado como ámbito de consulta debe tener usos compatibles con los
objetivos que se le pregunten.

Haskell ofrece las tres piezas con otras construcciones [@marlow2010haskell].
@Lst:s2-4-haskell escribe el mismo caso como un módulo con lista de
exportación.

```haskell {#lst:s2-4-haskell caption="El mismo caso como módulo de Haskell" run=none}
module Expedientes (Person (..), closeCase) where

data Person = Ana | Bob deriving (Eq, Show)

served :: [Person] -> Person -> Bool
served notified p = p `elem` notified

closeCase :: Person -> [Person] -> [Person] -> Bool
closeCase p notified paid = served notified p && p `elem` paid

-- En otro módulo:
--   import qualified Expedientes as E
--   anaCase = E.closeCase E.Ana
```
::: explanation
La lista de exportación oculta `served`: quien importa el módulo sólo ve
`Person` y `closeCase`. El import cualificado evita choques de nombres con
el prefijo `E.`. `E.closeCase E.Ana` es una aplicación parcial, como
`Case(ana)`. Residuum no tiene equivalente para la exportación ni para la
cualificación.
:::

La separación entre interfaz e implementación sólo existe en un harness de
tests. El experimento de interfaz de `owns` compara una garantía publicada con
una cláusula de la implementación. El documento aclara que es un checker de
tests, no una capacidad del compilador. La auditoría marca `interface`,
`Contract` y `ensures` como **NOT IMPLEMENTED**.

## Veredicto

Residuum divide un programa en ficheros con imports comprobados. Reutiliza
reglas mediante Programs, RuleUses y aplicación parcial, sin copiar cuerpos.
Le faltan la ocultación y los espacios de nombres. La interfaz verificada
sólo existe en tests.

Según este criterio, Residuum ofrece un desempeño medio: reutiliza reglas sin copiarlas mediante imports, Programs y aplicación parcial, pero todo símbolo es público y no hay espacios de nombres ni interfaces.
