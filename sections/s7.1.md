Usar Residuum a diario no exige un entorno especial. Basta un fichero `.res`
y una orden. Esa orden pasa siempre por el mismo programa, el launcher, que
impone límites de memoria y tiempo. Esta parte del libro trata lo que el
usuario encuentra al trabajar con el lenguaje, desde los límites de recursos
hasta el estilo. Esta sección presenta tres hábitos que las demás dan por
supuestos.

## El launcher

<!-- covers: 1 -->

El ejecutable `residuum` de la raíz del repositorio es el launcher seguro. Es
un script de Python que admite cuatro órdenes:

```sh
./residuum run fichero.res
./residuum query fichero.res
./residuum explain fichero.res
./residuum execute fichero.res
```

`run` calcula el cierre hacia delante y comprueba cada objetivo. `query`
ejecuta la consulta declarada en cada experimento. `explain` muestra las
justificaciones y la selección de defaults. `execute` hace lo mismo que `run`
y después aplica los efectos al estado (@sec:s7.4). Todas salvo `execute` admiten
`--steps N` y `--trace` para la evaluación por pasos (@sec:s6.6).

El launcher no evalúa nada por sí mismo. Comprueba los argumentos y cede el
proceso a `scripts/test_safe.py`. Ese runner compila el worker Rust en modo
incremental y lo ejecuta dentro de un cgroup con límites (@sec:s7.2). La
salida del programa va a stdout y los diagnósticos a stderr. Para usar
`residuum` desde otra carpeta, se añade la raíz del repositorio al `PATH`. El
launcher requiere Linux, cgroup v2 y una sesión de systemd del usuario. Sin
ellos falla y no ejecuta nada.

## Las fixtures como programas

<!-- covers: 2 -->

En Residuum, un programa y su caso de prueba son el mismo fichero. Una fixture
es un fichero Formal que lleva declaraciones, datos y consultas
(`docs/executable-fixtures.md`). Sus experimentos escriben los hechos de
entrada en `seeds { … }` o las hipótesis lógicas en `premises { … }`. Rust
parsea, elabora y ejecuta la fixture. Los tests comprueban resultados sin
fabricar en Rust sus eventos de entrada.

El recorrido es siempre el mismo:

```text
archivo .res → parser → SurfaceAST → TypedAST → consulta/cierre → salida
```

Cada experimento tiene una entrada independiente. Los escenarios no se mezclan
y una consulta no afirma sus requisitos como hechos. La CLI exige al menos un
bloque `experiment` local en el fichero.

## El flujo de trabajo de los experimentos

<!-- covers: 3 -->

El trabajo con Residuum avanza por experimentos. Un experimento nuevo suele
seguir estos pasos:

1. Se escribe una fixture con las declaraciones, las reglas y varios
   escenarios.
2. Se ejecuta con el launcher, o con `python3 scripts/test_safe.py --fixture
   <archivo.res>`, bajo los mismos límites.
3. Se registra la salida observada en un documento de `docs/`, con su tabla
   de resultados.
4. Se añaden tests individuales que fijan esa salida, y se ejecutan uno a uno
   con el runner.

`docs/executable-fixtures.md` sigue ese patrón con `ResidualProof`. La fixture
contiene tres escenarios. El documento da la orden y una tabla con el
requisito de cada uno. En la verificación original de ResidualProof y
FourCounterexample se ejecutaron seis tests nuevos y tres regresiones, uno a
uno.

El runner tiene modos propios para otros experimentos. `--forward` observa el
cierre con programas activos. `--incremental` compara la actualización
incremental con una recomputación completa sobre los bloques `base` y `delta`.
@Sec:s7.8 describe cómo estas fixtures se convierten en tests de regresión.
