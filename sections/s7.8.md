Un buen programa Residuum se reconoce por cómo se comprueba. El repositorio
sigue cuatro convenciones. Los datos y las consultas van en el propio fichero.
Las fixtures sirven de tests de regresión. Cada afirmación de los documentos
lleva su clase. La integración continua repite las comprobaciones en cada
cambio. Esta sección las describe en ese orden.

## Experimentos en el fichero

<!-- covers: 1 -->

Un programa declara sus escenarios en bloques `experiment`, junto a las
declaraciones y las reglas (`docs/executable-fixtures.md`). Cada experimento
tiene su propia entrada, y la entrada tiene una clase fija:

- `seeds { … }` para hechos de entrada, que exige la consulta residual;
- `premises { … }` para hipótesis lógicas, que exige `fourFusion`.

Las dos no se mezclan. Una premisa no afirma que una proposición `derived` se
haya derivado fuera. Las entradas `seeds` sólo admiten verbos `seeded`. `seeds {}`
es conocimiento vacío, no `I`.

La convención tiene una consecuencia de estilo. Un escenario nuevo es un
bloque más en el fichero, no código de Rust. Los tests comprueban resultados
sin fabricar sus eventos de entrada. Los experimentos de un módulo importado
no se importan: cada fichero responde de los suyos (@sec:s2.4).

## Fixtures como tests de regresión

<!-- covers: 2 -->

Una fixture de `examples/` es a la vez ejemplo y test. La CLI y el runner de
fixtures la cargan con `load_formal_module`. Los tests de Rust la ejecutan y
comparan la salida con la esperada. `docs/executable-fixtures.md` da la orden para cada una y la salida
observada. Las fixtures se ejecutan una a una con `python3 scripts/test_safe.py
--fixture <archivo.res>`, bajo los límites del runner (@sec:s7.2).

Las fixtures sirven también de oráculo para las optimizaciones. Los barridos
de equivalencia recorren todas las fixtures de `examples/`. Comparan el
evaluador optimizado con el recorrido lineal y exigen la misma salida
(@sec:s7.6). Una fixture nueva entra así, sin más trabajo, en esas
comparaciones.

La convención tiene un coste declarado. Cada test de Rust que sólo carga un
`.res` engorda el binario de tests de la CLI. El inventario de compilación
propone ejecutar esas fixtures desde la CLI con su salida esperada. La palanca
figura como pendiente, porque requiere una salida JSON estable y resolver
`derivedAt` (`docs/compile-cost-optimizations.md`).

## Clasificación de las afirmaciones en los documentos

<!-- covers: 3 -->

Los documentos del repositorio no afirman «funciona» sin más. Cada afirmación
lleva una clase, en inglés, que dice qué la respalda. El README nombra tres
para la especificación del núcleo: obligaciones **THEOREM**, resultados
**MODEL RESULT** y comportamiento **EXPERIMENTAL OBSERVATION**, «con dominios
y límites explícitos». La auditoría final del núcleo monotónico define cinco
clases para sus garantías (`docs/monotonic-core-final-audit.md`):

| Clase | Qué la respalda |
|---|---|
| **THEOREM** | Un argumento matemático con sus hipótesis; no una prueba automática del código |
| **MODEL RESULT** | Una familia finita enumerada, con su dominio declarado |
| **IMPLEMENTED + TESTED** | Un camino implementado y un test aprobado con registro |
| **IMPLEMENTED + LIMITED** | Una implementación que necesita restricciones o precondiciones |
| **NOT IMPLEMENTED** | Una garantía o un mecanismo ausente del motor |

: Clases de afirmación de los documentos de Residuum {#tbl:s7-8-clases}

Las clases califican afirmaciones concretas, no módulos enteros. Un mismo
cierre puede tener un argumento THEOREM y regresiones IMPLEMENTED + TESTED.
Los documentos no colapsan esas afirmaciones en una etiqueta de «todo
demostrado». Este libro usa las clases de la misma manera y las atribuye al
documento que las asigna.

## CI

<!-- covers: 4 -->

La integración continua corre en GitHub en cada push y cada pull request
(`.github/workflows/ci.yml`). Es la única excepción a la regla del runner.
Las máquinas de GitHub son desechables y no tienen la sesión de systemd que el
runner necesita. Por eso la CI llama a `cargo` directamente. Conserva un hilo
de tests para que el orden y la escritura de informes sean los de local.

El flujo tiene estos pasos:

1. comprueba el formato con `cargo fmt --check`;
2. ejecuta `clippy` con los avisos como errores;
3. compila el binario release;
4. compila cada familia de tests sola y sin avisos, con Rust 1.87.0;
5. ejecuta la suite completa de la biblioteca y de la CLI, con un hilo;
6. ejecuta en release los barridos de las seis fixtures de carga;
7. exige que los informes versionados de `docs/legal-geometry` se reproduzcan
   sin diferencias.

El último paso falla si un test reescribió un fichero versionado. Así, un
cambio en la salida del motor no puede pasar sin revisión. Los tests ignorados
del frontend CNL pausado siguen ignorados y no cuentan para cerrar un cambio.
