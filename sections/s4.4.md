Todo evento de Residuum ocurre en un instante. El tiempo no es un argumento
más, sino parte del tipo del evento. Esta sección explica cómo se escribe un
tiempo, cómo se construye el instante siguiente y cuándo dos tiempos son el
mismo. La terminación de las reglas que avanzan en el tiempo es otro tema
(@sec:s6.11).

## `PropositionTime`

<!-- covers: 1 -->

`PropositionTime` es el tipo integrado de los instantes. Un instante concreto
se declara como constante:

```text
const tau : PropositionTime
```

Cada evento lleva un tiempo proposicional: `sells(juan, car, pedro) @ tau`.
El TypedAST guarda ese tiempo en el tipo de la proposición, junto con la clase
del verbo. El tiempo forma parte de la identidad lógica del evento. Dos
eventos con el mismo verbo y los mismos argumentos, pero en instantes
distintos, son eventos distintos.

`PropositionTime` también puede ser el tipo de un argumento o de un campo. La
ontología jurídica de los ejemplos usa `effective : PropositionTime` para la
fecha de vigencia de una norma. Esa fecha es un dato del evento, no su
instante. Un comentario de la fixture lo dice: `tau` indexa el expediente, y
no se identifica con la vigencia (@sec:s4.10).

El tiempo proposicional no es el sello de una derivación. El sello
(`derivedAt`) registra en qué paso del cierre se obtuvo una conclusión. Tiene
otro tipo interno y no se escribe en el código fuente.

## `after` como constructor

<!-- covers: 2 -->

`after` construye el instante siguiente a otro. Su firma es exactamente
`PropositionTime -> PropositionTime`. Es el único constructor de términos del
lenguaje.

`after` es simbólico. No suma uno, no consulta un calendario y no evalúa nada.
`after(tau)` es un término nuevo, formado por el constructor y su argumento.
Los constructores pueden anidarse en un argumento: `after(after(tau))`. La
elaboración comprueba el tipo de entrada en todas partes, también dentro de
records y de bindings de Program. Una entidad como `Natural` o un opcional no
pueden ser su argumento (`docs/temporal-constructors-experiment.md`).

El TypedAST representa un tiempo con tres casos (`TimeExpr`):

| Caso | Significado |
|---|---|
| `At(name)` | Una constante temporal |
| `Var(name)` | Un parámetro temporal de una regla |
| `After(t)` | El instante siguiente a `t` |

: Los casos de un tiempo en el TypedAST {#tbl:s4-4-casos}

Un tiempo usado como argumento se guarda como término. Las funciones
`to_term` y `from_term` traducen entre las dos formas. El documento del
experimento justifica tres leyes por inducción estructural: decodificar lo
codificado devuelve el original, en ambos sentidos, y la sustitución conmuta
con la codificación. Los tests (`src/temporal_term_tests.rs`) las comprueban
sobre 27 expresiones: tres raíces con profundidades de 0 a 8. Son tests
finitos que acompañan el argumento; no demuestran aritmética general.

## Parámetros de tiempo frente a constantes

<!-- covers: 3 -->

Un nombre de tiempo dentro de una regla es un parámetro o una constante. La
elaboración lo decide una sola vez. Si el nombre está en la cabecera de la
regla, es un parámetro (`Var`). Si no, debe ser una constante `PropositionTime`
declarada (`At`). Después ya no se consulta el código fuente para
reinterpretarlo.

La diferencia cambia lo que la regla significa. Un parámetro vale para
cualquier instante. Una constante sólo vale para ese instante. El matching
sólo liga parámetros; una constante se compara literalmente, también debajo de
`after`. @Lst:s4-4-plazo pone las dos formas en un mismo módulo.

```res {#lst:s4-4-plazo caption="Una regla que relaciona t y after t" run=run}
module Plazo

entity Person
const ana : Person
const tau : PropositionTime
const deadline : PropositionTime

seeded verb notified(person : Person)
derived verb mayAppeal(person : Person)
derived verb archived(person : Person)

// t es un parámetro: la regla vale para cualquier instante.
rule appeal(person, t) = notified(person) @ t <= mayAppeal(person) @ after t

// deadline es una constante: la regla sólo vale para ese instante.
rule closing(person) = notified(person) @ deadline <= archived(person) @ after deadline

experiment sameInstant {
    seeds { notified(ana) @ tau, }
    query residual mayAppeal(ana) @ tau
}

experiment nextInstant {
    seeds { notified(ana) @ tau, }
    query residual mayAppeal(ana) @ after tau
}

experiment fixedInstant {
    seeds { notified(ana) @ tau, }
    query residual archived(ana) @ after deadline
}
```
::: explanation
La regla `appeal` liga `t` con `tau` y concluye `mayAppeal(ana) @ after(tau)`.
El objetivo de `sameInstant` pide el mismo evento en `tau`, y ese evento no
se deriva. El de `nextInstant` coincide con la conclusión. La regla `closing`
nunca se aplica: su antecedente exige el instante `deadline`, y el seed ocurre
en `tau`.
:::

Una constante y un parámetro pueden llamarse igual. La fixture
`temporal_identity_formal.res` declara `const t : PropositionTime` y una regla
con un parámetro `t`. En la cabecera, el parámetro tapa la constante. Al
aplicar parcialmente esa regla con la constante `t`, el primer tiempo queda
fijo en la constante y el segundo sigue libre. El TypedAST conserva la
diferencia: `At("t")` y `Var("t")` son valores distintos. En los
diagnósticos, un tiempo libre se muestra como `?t`.

Una regla puede dejar la cabecera vacía, como `rule implication() = ...`.
Entonces sus parámetros se infieren de los nombres que usa. Las constantes
declaradas quedan fuera: un nombre declarado como constante nunca se
convierte en parámetro (`docs/executable-fixtures.md`).

## La restricción sintáctica del tiempo de evento

<!-- covers: 4 -->

La posición `@` admite menos que un argumento. Tras `@` va un nombre (`@ tau`,
`@ t`) o `after` seguido de un nombre (`@ after t`). No se permite anidar:
`@ after(after(t))` es un error de parsing.

La restricción es sólo de la sintaxis. El TypedAST admite tiempos anidados, y
el cierre los produce. Una regla con conclusión en `@ after t` aplicada a un
evento en `after(tau)` concluye en `after(after(tau))`. Un tiempo anidado
también puede llegar a `@ t` a través de un parámetro. Los experimentos de
Peano construyen así índices como `after^5(zeroTime)`. Esa notación es una
abreviatura de los documentos, no sintaxis.

## Identidad temporal

<!-- covers: 5 -->

Dos tiempos son iguales cuando son el mismo término. La comparación es
estructural:

- `tau` y `after(tau)` son instantes distintos;
- `after(tau)` y `after(tau)` son el mismo instante;
- dos constantes con nombres distintos son instantes distintos, aunque el
  autor las piense como la misma fecha.

Residuum no ordena los instantes. No hay `<` entre tiempos ni se presupone
que `after` sea un sucesor de calendario. Si un dominio necesita comparar
fechas, debe declarar un verbo para ello. La ontología jurídica lo hace con
`notEarlier(later, earlier)`, un verbo `seeded`: la comparación es un dato de
entrada.

La identidad temporal tiene una consecuencia en la búsqueda. Un ciclo que
genera `t`, `after(t)` y así sucesivamente nunca repite un objetivo. Por eso
la búsqueda residual lo detiene por profundidad y no por repetición
(@sec:s6.8).

La representación del binding sigue esta misma regla. Si el parámetro es
temporal, `Term(Const("tau"))` y `Time(At("tau"))` se identifican. Si no lo es,
no se identifican. La conversión depende del tipo del parámetro, nunca de cómo
se escribe la constante (`docs/canonical-typed-substitutions.md`).
