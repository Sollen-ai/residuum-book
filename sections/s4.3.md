El subtipado permite que un valor de un tipo ocupe el lugar de otro más
general. En los lenguajes orientados a objetos es la base del polimorfismo de
inclusión [@cardelli1985understanding]. Residuum tiene una forma pequeña de
subtipado: sólo entre entidades, y sólo en ciertas posiciones. No tiene
ninguna otra conversión implícita entre tipos.

## Entidades con `<:`

<!-- covers: 1 -->

Una entidad declara su supertipo con `<:`:

```text
entity Person
entity Buyer <: Person
```

La declaración dice que todo `Buyer` vale donde se espera un `Person`. La
relación es transitiva. Si `Deep <: Special` y `Special <: Thing`, un `Deep`
vale donde se espera un `Thing`. El elaborador recorre la cadena de
supertipos declarados con un conjunto de visitados. Así, una declaración
circular no lo hace girar sin fin.

El subtipado no cambia el valor. Una constante `ana : Buyer` sigue siendo
`ana`, con su tipo declarado. Ningún evento ni ninguna sustitución reescribe
su identidad. Los documentos de los bindings explícitos lo dicen así: los
valores y los tipos suministrados se conservan, sin coerción de la constante
(`docs/residual-explicit-bindings-api.md`).

## Asignabilidad

<!-- covers: 2 -->

Residuum usa dos políticas de asignabilidad, ambas en `src/elab.rs`. La
política amplia (`rule_type_assignable`) acepta el tipo exacto, un subtipo de
entidad y un valor `T` donde se espera `T?`. La política estricta
(`is_assignable`) acepta el tipo exacto y los opcionales, pero no los
subtipos.

La política amplia rige en las posiciones raíz donde se nombra una constante:

- los argumentos de los eventos ground de un experimento;
- las constantes escritas dentro de una regla;
- los bindings con nombre de un RuleUse (`use r { x = c }`);
- los bindings de consulta (`with { rule r.x = c }`);
- los elementos del estado inicial.

La política estricta rige en otras posiciones:

- los campos de un record;
- los valores de un efecto `+=` o `-=`;
- los términos de las condiciones de un default.

Hay además posiciones que exigen igualdad exacta. La aplicación posicional de
una regla o de un Program exige que el tipo de la constante sea igual al tipo
del parámetro (@sec:s5.7). Si el primer parámetro de `P` es un `Thing`,
`P(child)` falla aunque `child` sea un subtipo de `Thing`. La asociación de un
verbo con su regla o Program también compara las firmas por igualdad.

@Lst:s4-3-sub muestra el caso aceptado. El verbo espera un `Person`, y el
seed le pasa un `Buyer`.

```res {#lst:s4-3-sub caption="Un valor de un subtipo, aceptado" run=run}
module Comprador

entity Thing
entity Person
entity Buyer <: Person

const ana : Buyer
const car : Thing
const tau : PropositionTime

seeded verb pays(subject : Person, object : Thing)
derived verb paid(subject : Person, object : Thing)

rule payment(person, object, t) = pays(person, object) @ t <= paid(person, object) @ t

experiment buyerPays {
    seeds { pays(ana, car) @ tau, }
    query residual paid(ana, car) @ tau
}
```
::: explanation
`ana` se declara como `Buyer`, y `Buyer <: Person`. El seed ocupa una
posición `Person` del verbo `pays`, que usa la política amplia. La regla
concluye `paid(ana, car)` y la línea `Horn` lo confirma. La constante
conserva su nombre en todo el resultado.
:::

@Lst:s4-3-super invierte la dirección. El verbo espera un `Buyer`, y el seed
le pasa un `Person`.

```res {#lst:s4-3-super caption="Un valor de un supertipo, rechazado" run=expect-error}
module Comprador

entity Thing
entity Person
entity Buyer <: Person

const juan : Person
const car : Thing
const tau : PropositionTime

seeded verb pays(subject : Buyer, object : Thing)
derived verb paid(subject : Buyer, object : Thing)

rule payment(buyer, object, t) = pays(buyer, object) @ t <= paid(buyer, object) @ t

experiment personPays {
    seeds { pays(juan, car) @ tau, }
    query residual paid(juan, car) @ tau
}
```
::: explanation
`juan` es un `Person`, y no todo `Person` es un `Buyer`. La elaboración
rechaza el seed antes de ejecutar el experimento. El subtipado sólo va hacia
arriba, del tipo más estrecho al más general.
:::

## Ninguna otra coerción

<!-- covers: 3 -->

Fuera de los dos casos anteriores, un valor nunca cambia de tipo:

- **Entidad y tiempo.** Una constante de entidad no se convierte en tiempo por
  su nombre (`docs/canonical-typed-substitutions.md`).
- **`none` y tiempo.** `none` no puede ser un `PropositionTime`.
- **Tiempo y números.** `PropositionTime` no es intercambiable con una
  entidad nominal como `Natural`, aunque los experimentos de Peano usen
  `after` como sucesor (`docs/temporal-constructors-experiment.md`).
- **Conjuntos.** No hay conversión entre un conjunto y sus elementos.

El opcional es el único caso fronterizo. Un `Thing` vale donde se espera un
`Thing?`, pero el valor no se envuelve: sigue siendo la misma constante. Es
asignabilidad, no conversión.

La inferencia de tipos de las reglas tampoco usa el subtipado. Si un parámetro
aparece en una posición `Person` y en otra `Buyer`, la elaboración da
«conflicting inferred types». Esta frontera se explica en @sec:s4.5.

La política doble tiene una consecuencia práctica. Un subtipo vale como
argumento raíz de un evento, pero no dentro de un record. Los documentos de
Residuum registran estas fronteras como políticas existentes. Ampliar la
aplicación posicional, por ejemplo, exigiría una propuesta aparte y su
revisión antes de implementarse.
