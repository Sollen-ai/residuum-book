Este criterio mide cuánto se parecen los tipos de un lenguaje a los datos de
sus programas. Un buen ajuste deja escribir cada dato con su forma propia:
una persona como persona, una fecha como fecha, un conjunto como conjunto.
Un mal ajuste obliga a codificar, por ejemplo una fecha como un número o una
lista como una cadena.

El criterio también mira las estructuras de datos. Una estructura agrupa
valores: un registro con campos con nombre, un conjunto sin repeticiones, un
valor que puede faltar. Cuantas más estructuras ofrece el lenguaje, menos
tiene que inventar el programador. Cada estructura añadida, sin embargo,
amplía lo que el lenguaje debe definir y comprobar.

## El criterio en Residuum

Los tipos de Residuum describen los objetos de un razonamiento con reglas. El
TypedAST tiene cinco formas de tipo: entidad, `Set`, opcional,
`PropositionTime` y el tipo del sello de derivación. Las reglas que los
combinan pertenecen a @sec:s4.1. Esta sección evalúa su ajuste a los datos.

<!-- covers: 1 -->

**Entidades.** `entity Person` declara un tipo nominal. Sus valores son
constantes declaradas, como `const ana : Person`. Una entidad puede ser
subtipo de otra con `<:` (@sec:s4.3). Las entidades se ajustan bien a los
participantes de un caso: personas, cosas, expedientes. Su límite es que una
regla no crea constantes nuevas. Si el caso tiene tres personas, el módulo
declara tres constantes.

<!-- covers: 2 -->

**Campos.** Una entidad puede declarar campos con tipo, como
`assets : Set Thing`. Los campos tienen dos usos. Describen el estado que
cambian los efectos (@sec:s7.4) y dan forma a los records.

<!-- covers: 3 -->

**Set.** `Set T` es un conjunto de valores de tipo `T`. Aparece en los campos
y en el estado inicial de un experimento, como `juan.assets = {car}`. Los
efectos añaden y quitan elementos con `+=` y `-=`. El TypedAST no tiene un
término de conjunto, así que un conjunto no puede ser argumento de un evento.

<!-- covers: 4 -->

**Opcional.** `Thing?` es una cosa o nada, y `none` es el valor vacío. Basta
para un dato que el caso puede no tener, como un garante. En el TypedAST,
`Set` y el opcional envuelven cualquier otro tipo. Los tipos, por tanto, se
pueden anidar.

<!-- covers: 5 -->

**Records.** Un valor record da valor a los campos de una entidad:
`Slot { first = tau, second = after(tau) }`. Según la referencia, el orden de
los campos no importa. Un record puede ser argumento de un evento y
contener tiempos construidos con `after`.

<!-- covers: 6 -->

**PropositionTime.** El tiempo de un evento tiene su propio tipo. Un instante
es una constante o `after` aplicado a otro instante. El tiempo no es un
número: no hay operaciones aritméticas sobre instantes (@sec:s4.4).

El TypedAST separa además dos clases de tiempo. `PropositionTime` es el
instante del que habla el evento. El sello de derivación es el instante en
que el motor obtuvo una justificación. El primero forma parte de la identidad
lógica del evento; el segundo, no. Un lenguaje sin esta separación tendría
que codificarla a mano.

@Lst:s2-3-reserva usa una entidad con campos, un subtipo, un record y un
opcional en una sola regla.

```res {#lst:s2-3-reserva caption="Una entidad con campos y un valor record usados en una regla" run=run}
module Reserva

entity Thing
entity Person {
    assets : Set Thing
}
entity Buyer <: Person
entity Slot {
    first : PropositionTime
    second : PropositionTime
}

const ana : Buyer
const car : Thing
const tau : PropositionTime

seeded verb books(subject : Person, slot : Slot, extra : Thing?)
derived verb reserved(slot : Slot, extra : Thing?)

rule booking(person, slot, extra, t) =
    books(person, slot, extra) @ t <= reserved(slot, extra) @ after t

experiment withExtra {
    seeds { books(ana, Slot { first = tau, second = after(tau) }, car) @ tau, }
    query residual reserved(Slot { second = after(tau), first = tau }, car) @ after tau
}

experiment withoutExtra {
    seeds { books(ana, Slot { first = tau, second = after(tau) }, none) @ tau, }
    query residual reserved(Slot { first = tau, second = after(tau) }, none) @ after tau
}
```
::: explanation
`ana` es un `Buyer` y vale donde el verbo espera un `Person`. El seed escribe
el record con los campos en el orden declarado. El objetivo de `withExtra`
los escribe al revés, y aun así se cumple. El segundo experimento usa `none`
como valor del opcional. La salida abrevia cada record como `Slot {...}`, así
que no muestra sus campos.
:::

<!-- covers: 7 -->

Tampoco hay listas ni tuplas. Un dato ordenado o repetido se escribe como
varios eventos, o como un record con un campo por posición.

Faltan dos tipos que casi todos los lenguajes traen: los números y las
cadenas. El TypedAST no tiene ningún tipo numérico ni de texto. Un importe,
una edad o un nombre propio deben ser constantes de una entidad. Esto basta
mientras el razonamiento sólo compara identidades. No basta cuando una regla
necesita calcular, como «el doble del precio», o comparar, como «mayor de
edad». @Sec:s2.1 muestra el precio de la aritmética codificada con `after`.

Haskell muestra el contraste [@marlow2010haskell]. @Lst:s2-3-haskell escribe
los mismos datos con números, cadenas y conjuntos.

```haskell {#lst:s2-3-haskell caption="Los mismos datos en Haskell" run=none}
import qualified Data.Set as Set

data Thing = Car deriving (Eq, Ord, Show)

data Person = Person
  { name   :: String
  , assets :: Set.Set Thing
  }

data Slot = Slot { first :: Int, second :: Int } deriving (Eq, Show)

data Booking = Booking
  { subject :: Person
  , slot    :: Slot
  , extra   :: Maybe Thing
  }

reserved :: Booking -> (Slot, Maybe Thing)
reserved b = (slot b, extra b)

nextSlot :: Int -> Slot
nextSlot t = Slot { first = t, second = t + 1 }
```
::: explanation
`String` e `Int` vienen con el lenguaje. `Maybe Thing` corresponde a
`Thing?`, y `Nothing` a `none`. `Data.Set` viene de la biblioteca
`containers`, no del informe del lenguaje. El tiempo es un `Int`, así que
`t + 1` sustituye a `after(t)`. Haskell no tiene subtipos: un `Buyer` exigiría
otro tipo o un constructor más.
:::

Haskell gana en cálculo y en datos generales. Residuum gana en una cosa
concreta: el tiempo de un evento tiene un tipo propio, distinto de cualquier
dato, y la elaboración rechaza un tiempo donde se espera una persona. El
constructor `after` tiene la firma `PropositionTime → PropositionTime`, así
que tampoco acepta una entidad como argumento.

## Veredicto

Los tipos de Residuum se ajustan a los participantes, los estados y los
instantes de un caso. Sus records y opcionales cubren datos estructurados
sencillos. La falta de números y de cadenas obliga a codificar cualquier
cantidad o texto.

Según este criterio, Residuum ofrece un desempeño medio: sus tipos se ajustan a los participantes y los instantes de un caso, pero no tiene números ni cadenas.
