El cierre responde qué se sigue de lo que ya se sabe (@sec:s6.3). Muchas
preguntas piden lo contrario: qué falta para llegar a un objetivo. Residuum
responde esa pregunta con una consulta residual. Su respuesta es un requisito
residual: una fórmula de seeds que, añadida como hipótesis a Known, basta para
derivar el objetivo. Esta sección explica cómo se escribe la regla, cómo se
busca el requisito y cómo se certifica.

La sección no trata dos capas vecinas. La búsqueda rechaza los módulos con
defaults (@sec:s6.9). El entailment FOUR es otra consulta, con otra semántica
(@sec:s6.10).

## Residuación: de la regla a lo que falta

En un retículo residuado, el producto tiene un residuo [@ward1939residuated].
En el caso conmutativo, la ley central dice que `a ⊗ b ≤ c` vale si y sólo
si `b ≤ a ⊸ c`. El residuo `a ⊸ c` es el mayor `b` que cumple `a ⊗ b ≤ c`.
Es lo que todavía falta, dado `a`, para llegar a `c`. La notación ⊗ y ⊸ es
también la de la lógica lineal [@girard1987linear].

Una regla de Horn de Residuum se escribe `A & B <= C`. Se lee «`A` y `B`
implican `C`». La cláusula residual escribe la misma regla en forma
currificada:

```text
A <= B -o C
```

Se lee «`A` implica `B -o C`»: dado `A`, todavía falta `B` para concluir `C`.
La búsqueda usa la vista Horn equivalente de cada cláusula residual. Los tests
de la consulta cubren esa equivalencia entre la forma Horn y la residual
currificada (`docs/program-residual-query.md`).

Para la búsqueda, la forma residual no añade poder: muestra qué premisa queda
pendiente. Los documentos de Residuum no afirman más. La búsqueda actual no
demuestra una realización del adjunto general. La relación objetivo general
del residual «sigue abierta».

## Los requisitos como hipótesis

Peirce llamó abducción al paso que va de un hecho sorprendente a la hipótesis
que lo explicaría [@peirce1934collected]. La programación lógica abductiva
fija ese paso: dado un programa y un objetivo, busca un conjunto de hechos
abducibles que, unido al programa, implica el objetivo y respeta sus
restricciones de integridad [@kakas1992abductive].

Residuum adopta esa forma con tres decisiones propias:

- **Qué es abducible.** Por defecto, todo verbo `seeded` es abducible, en sus
  dos polaridades: positiva y con negación evidencial. Una API opcional
  restringe las hipótesis por verbo y polaridad. Un verbo `derived` o
  `effect` nunca se abduce: se resuelve mediante reglas.
- **Dónde viven las hipótesis.** Una hipótesis es una propuesta explícita,
  separada de los hechos reales. Nunca entra en Known ni recibe sello. Una
  hipótesis negativa tampoco nace de la ausencia de un hecho.
- **Qué forma tiene la respuesta.** El requisito es una fórmula, no un
  evento ni una unión de Known.

La fórmula del requisito (`RequirementFormula`) tiene cuatro formas:

| Forma | Significado |
|---|---|
| `I` (`Unit`) | No falta evidencia en esa explicación |
| Un evento | Falta ese seed, admitido como hipótesis |
| `H1 ⊗ H2` (`Tensor`) | Ambos requisitos pertenecen a la misma rama |
| `H1 ∨ H2` (`Join`) | Alternativas de explicación |

: Las formas del requisito residual {#tbl:s6-8-formas}

`I` no significa que Known esté vacío. Es el producto de cero factores: no
queda requisito adicional. Cuando no hay ninguna explicación admisible, el
resultado no es `I`. El campo `required` vale `None` y un campo `failure`
dice por qué.

Leída como conjunto de evidencias, cada respuesta denota en un modelo finito
una implicación de Heyting: lo que falta, dada la evidencia, para entrar en el
requisito del objetivo. @Sec:s6.14 da ese significado; aquí interesan la
búsqueda y la certificación.

```res {#lst:s6-8-venta caption="Un requisito encontrado y certificado" run=query}
module Venta

entity Thing
entity Person {
    assets : Set Thing
}

const alice : Person
const bob : Person
const car : Thing
const tau : PropositionTime

seeded verb agreesPrice(subject : Person, object : Thing, recipient : Person)
seeded verb agreesObject(subject : Person, object : Thing, recipient : Person)
seeded verb donates(subject : Person, object : Thing, recipient : Person)

effect verb give(subject : Person, object : Thing, recipient : Person) =>
    subject.assets -= object
    recipient.assets += object

// Cláusula residual: dado el acuerdo de precio, falta el de objeto.
rule sales(debtor, object, creditor, t) =
    agreesPrice(debtor, object, creditor) @ t
    <= agreesObject(creditor, object, debtor) @ t
    -o give(debtor, object, creditor) @ after t

// Cláusula de Horn: una donación también produce la entrega.
rule gift(donor, object, donee, t) =
    donates(donor, object, donee) @ t <= give(donor, object, donee) @ after t

experiment empty {
    seeds {}
    query residual give(alice, car, bob) @ after tau
}

experiment priceOnly {
    seeds { agreesPrice(alice, car, bob) @ tau, }
    query residual give(alice, car, bob) @ after tau
}

experiment both {
    seeds {
        agreesPrice(alice, car, bob) @ tau,
        agreesObject(bob, car, alice) @ tau,
    }
    query residual give(alice, car, bob) @ after tau
}
```
::: explanation
El módulo adapta la fixture `examples/experiments/residual_proof.res`. Añade
una segunda regla, `gift`, para que haya dos caminos hacia la entrega. Sin
seeds, el requisito une con `∨` el producto de los dos acuerdos y la donación.
Con el acuerdo de precio, sólo falta el acuerdo de objeto o la donación. Con
ambos acuerdos, la consulta conserva `I` junto a la alternativa de la
donación: no elige entre ramas.
:::

@Lst:s6-8-venta muestra las tres formas en un solo módulo. El experimento
`both` deja ver una decisión de diseño. La consulta conserva la rama `I` y
también la rama de la donación. Residuum no selecciona explicaciones mínimas
ni preferidas. Tampoco absorbe una alternativa en otra. El resumen sólo
consolida fórmulas con el mismo árbol, porque el join es idempotente. Aun así,
conserva por separado cada prueba.

El harness jurídico `LegalAbduction` comprueba la minimalidad de otra manera.
Para cada hipótesis propuesta, repite la cadena sin ella y verifica que la
explicación se pierde. Esa comprobación vale en sus ejemplos positivos
monotónicos. No es un selector de la consulta.

## Búsqueda con SearchLimits

La consulta busca hacia atrás, desde el objetivo hacia los seeds; @sec:s5.3
compara esa dirección con la derivación hacia delante. Para cada evento
pendiente, la búsqueda sigue cinco pasos:

1. Si el evento está en la evidencia, devuelve `I` y guarda el evento como
   testigo.
2. Si es un seed ausente, lo propone como hipótesis sólo si su verbo y su
   polaridad son abducibles.
3. Si es `derived` o `effect`, examina todas las reglas. Unifica cada cabeza
   con el objetivo y sustituye el antecedente con esos bindings.
4. Expande los eventos del antecedente. Una conjunción combina el producto
   cartesiano de las explicaciones de sus operandos.
5. Filtra los requisitos finales por admisibilidad y los certifica antes de
   resumirlos con `Join`.

El fragmento admitido es estrecho. El objetivo y la evidencia son ground.
Cada parámetro de una regla cuya cabeza coincide debe quedar fijado por esa
cabeza o por un binding explícito. La búsqueda no enumera dominios de objetos
para resolver variables libres del cuerpo. Los tiempos `after` conservan su estructura (@sec:s4.4).

`SearchLimits` acota la búsqueda con tres valores:

| Límite | Qué cuenta | Valor por defecto |
|---|---|---|
| `max_depth` | Profundidad, incluida la recursión en los antecedentes; de 1 a 64 | 32 |
| `max_nodes` | Visitas a eventos y antecedentes | 4096 |
| `max_branches` | Ramas construidas, intermedias y finales | 4096 |

: Los límites de la búsqueda residual {#tbl:s6-8-limites}

Un ciclo que genera tiempos distintos, como `t`, `after(t)` y así
sucesivamente, no repite la misma identidad. Lo detiene la profundidad. Estos
límites son algorítmicos. Acompañan los límites de proceso del runner, pero no
los sustituyen (@sec:s7.2).

La búsqueda falla con un error explícito en tres casos:

- una variable que la cabeza no determina;
- un ciclo de objetivos lógicamente iguales;
- un límite agotado.

En los tres casos devuelve `Err` y descarta toda la evaluación. Nunca entrega
un prefijo de resultados como si fuera completo. Las métricas del resultado
cuentan visitas, reglas examinadas, cabezas compatibles y ramas construidas.

## Certificación por replay

Encontrar un candidato no basta. Cada explicación lleva una prueba finita
(`ResidualProof`). Sus hojas son eventos de Known, hipótesis admisibles o `I`.
Cada paso intermedio guarda la regla aplicada, su objetivo y su sustitución.

El replay recorre esa prueba hacia delante. En cada aplicación de regla,
`instantiate_from_witness` procesa los antecedentes en el orden del cuerpo.
Usa las mismas operaciones de matching, sustitución y comprobación que el
cierre hacia delante. No busca combinaciones ni toma bindings del objetivo
para completar una instancia. El replay exige, además, que el evento
resultante sea el objetivo de ese paso.

Por inducción sobre la prueba se obtiene la garantía T10, de suficiencia
certificada. La auditoría del núcleo monotónico la clasifica como **THEOREM**
condicional:

```text
H devuelto por la consulta ⇒ G ∈ Close_R(Π)(K ∪ Leaves(H))
```

`R(Π)` es el conjunto de reglas del módulo, tratadas como cláusulas
explícitas. La garantía vale aunque el cierre completo fuera infinito por
otras reglas: el certificado sigue siendo una derivación finita del objetivo.
La consulta no ejecuta ese cierre, no asigna sello y no ejecuta efectos
(@sec:s7.4).

Un candidato que no pasa el replay se descarta. El resultado distingue así
dos fallos:

- `NotAbducible`: ninguna explicación usa sólo seeds admitidos;
- `NotForwardSupported`: había candidatos, pero ninguno tenía una prueba que
  el matching hacia delante pudiera ejecutar.

La fixture `Legal.sales_delivery` muestra un candidato descartado. La regla
genérica `traditio` se descarta porque su parámetro `conduct` no se resuelve hacia delante. La especialización `delivery`, en
cambio, pasa el replay. La fixture `alternatives_formal.res` comprueba
suficiencia y cobertura con un oráculo finito: recorre las 16 evidencias y
las 16 extensiones posibles de sus cuatro seeds. Ninguna de estas pruebas
demuestra completitud general.

## Consultas residuales activas

T10 habla de reglas tratadas como cláusulas aisladas. Un Program asociado a
un verbo se comporta de otro modo en el cierre (@sec:s5.6). Su definición
deja de ser una regla ordinaria y exige un trigger positivo conocido. Por
eso T10 no implica suficiencia bajo `close_program`.

El contrato de activación lo muestra como **MODEL RESULT** con la fixture
`associated_program_waits.res`. Su Known contiene `ready(juan) @ tau`, pero
no `starts(juan)`. El objetivo es `done(juan) @ after tau`. La consulta
residual de cláusulas aisladas devuelve `I`. Sin embargo, el cierre real del
módulo sólo deriva el objetivo si se añade el trigger `starts(juan) @ tau`.

La consulta residual activa (`query active residual`) cubre ese hueco:

- busca en una vista con las guardas positivas de `Verb.program`;
- certifica cada respuesta con el `close_program` original sobre evidencia
  hipotética, no con el replay Horn;
- conserva en cada explicación certificada las activaciones y sus productores
  reales.

Su garantía está condicionada a que el cierre termine:
`G ∈ Close_Π(K ∪ Leaves(H))`. `SearchLimits` acota la búsqueda, pero no el
cierre hipotético. La terminación queda a cargo del llamador y del entorno
acotado (@sec:s6.11).

La consulta activa tiene límites declarados. Sólo activan triggers positivos
de verbos `seeded` o `derived`. Un `effect` no activa programas asociados.
Rechaza los defaults y no cambia su selección. No afirma completitud ni que la
ruta residual sea la única prueba hacia delante.

El contrato marca como **NOT IMPLEMENTED** la integración de su garantía en la
consulta residual. También marca así la reevaluación hipotética de defaults y
una nueva resolución existencial. La API activa se añadió como una consulta
aparte. La consulta `query residual` conserva su semántica de cláusulas Horn
explícitas.

## Ámbitos y bindings explícitos

Una consulta sin ámbito busca en todas las reglas del módulo. Una consulta con
ámbito busca sólo en las reglas elegidas. Si el módulo declara un Program, cada
consulta residual debe ser activa o declarar su ámbito. La sintaxis tiene dos formas:

- `using rules { r1, r2 }`, con bindings `with { rule r1.x = c }`;
- `using program P`, con bindings `with { program P.x = c }`.

Un binding es una restricción. No es evidencia ni cambia la teoría. Un
binding de regla se refiere a la lambda original, también en cada RuleUse que
la compila. Un binding de Program se refiere al Program resuelto, quizá
aplicado parcialmente (@sec:s5.7). Sólo admite los parámetros compartidos que
quedan libres. Dos reglas ordinarias nunca comparten un binding sólo porque
sus parámetros se llamen igual.

```res {#lst:s6-8-ambito caption="Lo mismo con un ámbito explícito" run=query setup=s6-8-venta}
program Sale(debtor : Person, object : Thing, creditor : Person, t : PropositionTime) {
    use sales { debtor = debtor, object = object, creditor = creditor, t = t }
}

experiment boundRule {
    seeds { agreesPrice(alice, car, bob) @ tau, }
    query residual give(alice, car, bob) @ after tau
    using rules { sales }
    with { rule sales.creditor = bob, rule sales.t = tau }
}

experiment boundProgram {
    seeds { agreesPrice(alice, car, bob) @ tau, }
    query residual give(alice, car, bob) @ after tau
    using program Sale
    with { program Sale.creditor = bob }
}
```
::: explanation
El listado reutiliza el módulo de @lst:s6-8-venta como setup oculto. Añade un
Program `Sale` con un único uso de `sales`. Las dos consultas repiten el caso
`priceOnly` con un ámbito explícito. La regla `gift` queda fuera del ámbito,
así que la alternativa de la donación desaparece. Los bindings coinciden con
el objetivo; por eso el requisito no cambia dentro de `sales`.
:::

En @lst:s6-8-ambito el ámbito cambia la respuesta. Sin ámbito, el caso
`priceOnly` tenía dos ramas. Con ámbito, queda una. Un requisito hallado en
un ámbito se certifica con las reglas de ese ámbito. La ausencia de
explicación sólo dice que esas reglas, con esos bindings, no dan ninguna.

El ámbito no relaja la certificación: el replay usa los productores
originales. La validación rechaza como error, entre otros casos:

- un parámetro desconocido o un ámbito fuera de las reglas elegidas;
- un tipo incorrecto;
- un binding duplicado o inconsistente;
- un conflicto con una especialización fija de un RuleUse;
- un conflicto con la cabeza, incluso si Known ya contiene el objetivo.

Un binding exige `using`. Si la búsqueda recursiva llega a un productor con
parámetros sin resolver, el error enumera todos esos parámetros con su tipo.
Tampoco aquí se enumeran dominios.

Dos fronteras de tipos quedan documentadas. En un archivo `.res`, un record
literal se normaliza al orden de su declaración. La API tipada de Rust, en
cambio, conserva el orden recibido: allí dos permutaciones son valores
distintos. Para los subtipos, un binding de entidad usa la política de
asignación de los RuleUse con nombre (@sec:s4.3).

## Lo que la consulta no promete

Los documentos de Residuum dan por cerrado este bloque: búsqueda y abducción
monotónicas quedan congeladas en el estado descrito. Sus límites son parte del
contrato:

- **No hay completitud general.** La consulta garantiza suficiencia, no que
  encuentre toda explicación posible.
- **No hay preferencia.** No existen `minimal`, `preferred`, cardinalidad ni
  selección mediante el orden lógico `≤_L`.
- **No hay enumeración de dominios.** Sólo objetivos ground con parámetros
  fijados por la cabeza.
- **No hay defaults ni efectos.** La búsqueda rechaza los defaults y nunca
  modifica `State`.
- **Las hipótesis no son hechos.** Ningún requisito entra en Known.

Dos cuestiones siguen pendientes según la propia documentación. La relación
objetivo general del residual sigue abierta. La reevaluación de defaults bajo
hipótesis requeriría otro contrato, también pendiente.
