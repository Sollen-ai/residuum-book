Un lenguaje está bien definido cuando cada programa que acepta tiene
exactamente un significado. El criterio tiene dos caras. La primera es el
rechazo: un texto sin significado claro no debe pasar como programa. La
segunda es la unicidad: un programa aceptado no debe significar cosas
distintas según la máquina, la ejecución o el orden en que se escribió.

El criterio se examina en cuatro capas. La sintaxis y la comprobación
estática deciden qué textos son programas. La evaluación debe dar el mismo
resultado siempre que el significado lo exige. La forma de superficie que lee
el autor debe corresponder a una forma interna explícita. Por último, el
lenguaje debe decir qué ocurre ante un conflicto o una pregunta que no sabe
responder.

## Determinación sintáctica y estática

<!-- covers: 1.1 -->

El pipeline activo de Residuum es Formal → SurfaceAST → TypedAST →
derivación (@sec:s1.4). Un parser hecho con la biblioteca chumsky produce el
SurfaceAST. La auditoría del núcleo monotónico clasifica ese camino como
**IMPLEMENTED + TESTED**. Su evidencia es una regresión que compara el
SurfaceAST del parser con el de un parser manual en 25 fixtures. La misma
auditoría advierte que eso no prueba la corrección de toda la gramática.

Los documentos no contienen una prueba de que la gramática sea no ambigua.
Lo que sí fijan es la frontera entre notación y sintaxis. La auditoría
encontró que un documento usaba `⊗` como si fuera sintaxis. El lexer sólo
acepta `&`, y se corrigió el documento, no el parser. La gramática formal se
describe en @sec:s3.2.

La referencia del lenguaje añade una comprobación más. Un test extrae todos
sus bloques `res` y comprueba que se analizan y elaboran. Así, cada ejemplo
de la referencia es un programa aceptado. El test no dice que cada texto
tenga un solo análisis. Sí impide que la referencia muestre una forma que el
parser rechaza.

<!-- covers: 1.2 -->

La elaboración comprueba los tipos antes de evaluar. Un tiempo sin declarar
falla durante la elaboración. Lo mismo ocurre con un argumento desconocido,
una aridad incorrecta o un tipo incompatible. @Lst:s2-2-maltipado invierte
los argumentos de un evento.

```res {#lst:s2-2-maltipado caption="Un evento mal tipado, rechazado" run=expect-error}
module MalTipado

entity Person
entity Thing

const ana : Person
const book : Thing
const tau : PropositionTime

seeded verb requests(subject : Person, object : Thing)

experiment swapped {
    seeds { requests(book, ana) @ tau, }
    query residual requests(book, ana) @ tau
}
```
::: explanation
El verbo `requests` espera una persona y luego una cosa. El experimento
escribe `book` en el lugar de la persona. La elaboración rechaza el módulo
antes de calcular ningún cierre. El mensaje nombra la constante y el tipo
que esperaba.
:::

<!-- covers: 1.3 -->

Cada nombre declarado designa una sola cosa. El resolver de módulos rechaza
un símbolo declarado dos veces, en el mismo fichero o en dos ficheros
importados. Sólo acepta la repetición cuando las dos copias vienen del mismo
origen, como en un import en diamante (@sec:s2.4).

```res {#lst:s2-2-duplicado caption="Un símbolo duplicado, rechazado" run=expect-error}
module Duplicado

entity Person
const ana : Person
const ana : Person
const tau : PropositionTime

seeded verb known(person : Person)

experiment e {
    seeds { known(ana) @ tau, }
    query residual known(ana) @ tau
}
```
::: explanation
La constante `ana` aparece dos veces con el mismo tipo. Aun así, el resolver
no elige una de las dos. El mensaje nombra el símbolo y los dos orígenes, que
aquí son el mismo fichero.
:::

## Previsibilidad de la evaluación

<!-- covers: 2.1 -->

El significado de un módulo monotónico es su menor cierre (@sec:s6.3). La
auditoría clasifica como **THEOREM** que ese cierre es extensivo, monótono e
idempotente. El cierre depende del conjunto de reglas, no de su orden en el
fichero. El operador de consecuencia inmediata usa todas las reglas a la vez,
y el menor punto fijo no depende de cómo se enumeren. Los tests de la
evaluación por pasos cubren además el orden de las reglas.
@Lst:s2-2-orden-a y @lst:s2-2-orden-b escriben las mismas cuatro reglas en
órdenes opuestos.

```res {#lst:s2-2-orden-a caption="Cuatro reglas en un orden" run=run setup=s2-2-orden}
rule employment(p, t) = hired(p) @ t <= employee(p) @ t
rule insurance(p, t) = employee(p) @ t <= insured(p) @ t
rule access(p, t) = employee(p) @ t <= badge(p) @ t
rule coverage(p, t) = insured(p) @ t & badge(p) @ t <= covered(p) @ t

experiment hiredAna {
    seeds { hired(ana) @ tau, }
    query residual covered(ana) @ tau
}
```
::: explanation
Un setup oculto declara el módulo `Orden`, la persona `ana`, el tiempo `tau`
y cinco verbos. La contratación implica ser empleado. Ser empleado implica
el seguro y la credencial, y ambos implican la cobertura. El cierre deriva
los cuatro eventos y cumple el objetivo.
:::

```res {#lst:s2-2-orden-b caption="Las mismas reglas en el orden inverso" run=run setup=s2-2-orden}
rule coverage(p, t) = insured(p) @ t & badge(p) @ t <= covered(p) @ t
rule access(p, t) = employee(p) @ t <= badge(p) @ t
rule insurance(p, t) = employee(p) @ t <= insured(p) @ t
rule employment(p, t) = hired(p) @ t <= employee(p) @ t

experiment hiredAna {
    seeds { hired(ana) @ tau, }
    query residual covered(ana) @ tau
}
```
::: explanation
El conjunto de Known es el mismo que en @lst:s2-2-orden-a. Sólo cambia el
orden en que se imprimen `insured` y `badge`. Ese orden refleja el
descubrimiento de los eventos, no su significado.
:::

Un significado bien definido no garantiza una respuesta. La auditoría
clasifica el cierre Horn como **IMPLEMENTED + LIMITED**: para retornar, el
algoritmo necesita que el cierre se estabilice. Una regla que produce
`after t` a partir de `t` tiene un cierre infinito. Ese programa tiene
significado, pero su cierre completo no termina. Los límites del entorno lo
detienen (@sec:s6.11).

<!-- covers: 2.2 -->

El orden de descubrimiento sí deja huella en los sellos. Cada justificación
nueva recibe un sello `derivedAt` de un reloj externo. Con las reglas
permutadas, `insured` y `badge` pueden recibir sellos en otro orden. Los
documentos declaran esa diferencia:

- La auditoría (T7) no exige que dos ejecuciones sigan el mismo orden.
- El alcance de v1 dice que el valor concreto de `derivedAt` depende del
  reloj de la ejecución.
- El experimento de sustituciones canónicas compara sin el orden de
  descubrimiento ni el valor de `derivedAt`. Compara eventos, reglas,
  testigos y sustituciones.

El experimento de Peano lo comprueba en un caso concreto. Cambiar el reloj de
derivación conserva los eventos y los registros de derivación, y sólo cambia
los sellos.

Prolog muestra el riesgo contrario. Su resolución recorre las cláusulas en
orden textual y en profundidad [@sterling1994art]. En @lst:s2-2-prolog, el
orden de las cláusulas decide si la consulta termina.

```prolog {#lst:s2-2-prolog caption="En Prolog, el orden de las cláusulas importa" run=none}
edge(a, b).

% Orden 1: la cláusula recursiva va primero.
path(X, Y) :- path(X, Z), edge(Z, Y).
path(X, Y) :- edge(X, Y).

% ?- path(a, b).
% No termina: path/2 se llama a sí mismo antes de leer edge/2.
% Con las dos cláusulas de path/2 en el orden inverso,
% la primera respuesta es true.
```
::: explanation
La primera cláusula de `path/2` empieza por una llamada a `path/2` con el
mismo primer argumento y el segundo libre. La búsqueda en profundidad repite esa llamada sin
fin. Si la cláusula de `edge/2` va primero, la consulta encuentra antes la
respuesta. El significado lógico de las dos versiones es el mismo; su
comportamiento no.
:::

## Significado de superficie y significado de bajo nivel

<!-- covers: 3.1 -->

La superficie escribe igual cosas que el TypedAST distingue. Un nombre como
`t` puede ser un parámetro de la regla o una constante. El TypedAST separa
los dos casos: sólo los nombres de los parámetros de la regla son variables,
y los demás tiempos son literales. La auditoría clasifica esta distinción
como **IMPLEMENTED + TESTED**. Es la corrección F1 de la auditoría,
y tiene su propia regresión de cierre, replay e incrementalidad.

Las sustituciones también tienen una forma canónica. El tipo del parámetro
decide cómo se guarda el valor:

- un parámetro `PropositionTime` guarda un tiempo (`SubstitutionValue::Time`);
- cualquier otro parámetro guarda un término (`SubstitutionValue::Term`).

Así, `tau` como término y `tau` como tiempo se identifican sólo cuando el
parámetro es temporal. Un parámetro y una constante con el mismo nombre
siguen siendo valores distintos. Antes de esta regla, una misma conclusión
podía guardar dos justificaciones que sólo diferían en la representación. La
corrección se hizo donde se guarda el binding, no debilitando la comparación.

El documento de las sustituciones canónicas comprueba la corrección en
modelos finitos. Un universo de seis hechos da 448 comparaciones exactas de
eventos y provenance. El cierre indexado y el recorrido lineal coinciden en
cierre, provenance y sellos. El propio documento advierte que son
regresiones, no una prueba general de equivalencia.

<!-- covers: 3.2 -->

Los Programs añaden otra traducción oculta (@sec:s5.6). `compile_program`
baja cada RuleUse a una regla propia. Da nombres internos higiénicos a los
parámetros compartidos y a los locales. Nunca une dos parámetros porque se
llamen igual. La provenance resuelve cada regla compilada a su Program, a su
regla original y a la posición del RuleUse.

## Conflicto y completitud

<!-- covers: 4.1 -->

Dos defaults pueden llevar a conclusiones opuestas. Residuum los selecciona
en tres pasos: aplicabilidad, bloqueo y prioridad (@sec:s6.9). No comprueba,
en cambio, si el resultado es consistente. @Lst:s2-2-defaults lo muestra en
la línea `consistency`.

```res {#lst:s2-2-defaults caption="La selección de defaults no comprueba la consistencia" run=run setup=s2-2-defaults}
experiment retention {
    seeds { sale(saleCase) @ tau, retentionAgreed(saleCase) @ tau, }
    query residual selected(saleCase, Retention) @ tau
}
```
::: explanation
El setup oculto es el módulo `Defaults` de la referencia del lenguaje. El
acuerdo de retención bloquea `NormalSale` y selecciona `RetentionSale`. La
salida informa la consistencia como `NotChecked`. Ningún paso de la selección
la ha comprobado.
:::

El contrato de consistencia de los Programs es experimental. Observa pares
de evidencia opuesta en un cierre hipotético, pero el motor conserva
`ConsistencyStatus::NotChecked`. Ninguna observación bloquea ni derrota un
default. El alcance de v1 deja fuera la resolución completa de conflictos
entre programas.

El documento del contrato muestra por qué la pregunta sigue abierta. Sus
fixtures examinan 24 observaciones de Programs reales. Una observación
individual no certifica la combinación de varios candidatos: dos defaults
pueden no oponerse por separado y oponerse juntos. Quedan por decidir qué
evidencia hace inadmisible un candidato y cómo se combina con la prioridad.
Hasta entonces, el motor selecciona defaults sin comprobar si sus
consecuencias se oponen.

<!-- covers: 4.2 -->

Residuum tiene dos lecturas de una misma teoría: el cierre de Horn y el
entailment FOUR (@sec:s6.10). No coinciden. Con `~Q` y la regla `P <= Q`,
todos los modelos FOUR satisfacen `~P`, pero el cierre de Horn no lo deriva.
La auditoría clasifica la comparación como **MODEL RESULT** (M2). La familia
enumerada tiene 4.016 teorías y 20.080 consultas. Hay cero fallos de
soundness y 680 fallos de completitud.

Cada consulta nombra la lectura que usa, así que la diferencia no es
ambigüedad: son dos preguntas distintas. `run` y `query residual` usan el
cierre de Horn. `query fourFusion` usa los modelos FOUR y muestra además la
respuesta de Horn. El lector ve las dos respuestas, cada una con su nombre.

<!-- covers: 4.3 -->

La auditoría también registra un caso de ambigüedad en la API. La función
`query_residual` devuelve una lista vacía en dos situaciones: cuando la
cabeza no es compatible y cuando no falta nada. `query_program_residual`, la
que usa la CLI, distingue tres resultados: sin explicación, `I` y error. La
salida de la CLI escribe `no explanation` o `I`, y nunca confunde los dos.

Cuando una pregunta queda fuera del fragmento admitido, Residuum la rechaza.
No devuelve una respuesta parcial:

- La consulta residual y FOUR rechazan los módulos con defaults
  (@lst:s2-2-sin-defaults).
- Un módulo con Programs exige consultas activas o con ámbito explícito.
- La búsqueda residual devuelve un error al agotar un límite. Nunca entrega
  un prefijo como si fuera completo (@sec:s6.8).

```res {#lst:s2-2-sin-defaults caption="Una consulta residual sobre un módulo con defaults, rechazada" run=expect-error cmd=query setup=s2-2-defaults}
experiment retention {
    seeds { sale(saleCase) @ tau, retentionAgreed(saleCase) @ tau, }
    query residual selected(saleCase, Retention) @ tau
}
```
::: explanation
Es el mismo módulo de @lst:s2-2-defaults, ahora con la orden `query`. La
consulta residual no sabe reevaluar defaults bajo hipótesis. Por eso rechaza
el módulo entero en lugar de ignorar los defaults.
:::

## Veredicto

En el núcleo monotónico, cada programa aceptado tiene un solo cierre, y ese
cierre no depende del orden de las reglas. La elaboración rechaza los tipos
incorrectos y los nombres duplicados. Los rechazos sustituyen a las
respuestas parciales. Quedan tres huecos declarados: no hay prueba de que la
gramática sea no ambigua, los sellos dependen del reloj y la consistencia de
los defaults no se comprueba.

Según este criterio, Residuum ofrece un desempeño alto: su núcleo monotónico da un solo significado a cada programa aceptado y rechaza lo que no sabe tratar, aunque la consistencia de los defaults queda sin comprobar.
