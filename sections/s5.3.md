Haskell evalúa una expresión sólo cuando hace falta su valor. Residuum no tiene
evaluación perezosa, pero sí ofrece dos maneras de usar una regla. El cierre aplica todas las reglas en cuanto puede, hacia delante, desde los
seeds. La
consulta residual parte de un objetivo y busca hacia atrás qué haría falta
para llegar a él. Las dos maneras leen las mismas reglas y dan respuestas de
distinta naturaleza. Esta sección compara cuándo actúa cada una, qué devuelve
y qué la detiene. Los algoritmos están en @sec:s6.5 y @sec:s6.8.

## El cierre: evaluación ansiosa hacia delante

El cierre parte de los seeds y aplica cada regla a todo lo conocido. Cada
conclusión nueva entra en Known y puede disparar otras reglas. El proceso se
repite hasta que no aparecen eventos nuevos. La especificación clasifica ese
comportamiento de `close` como **EXPERIMENTAL OBSERVATION** E5: itera hasta que
no aparecen claves nuevas, deduplica eventos y conserva las justificaciones
distintas.

La evaluación es ansiosa en un sentido preciso. El cierre no mira el
objetivo. Deriva todo lo que se sigue, lo pida alguien o no. El objetivo de un
experimento es sólo una observación: después del cierre se comprueba si está
en Known. Kowalski describió este contraste como una elección de control sobre
la misma lógica [@kowalski1979algorithm]. El razonamiento hacia delante parte
de los datos y el razonamiento hacia atrás parte del objetivo.

Residuum tiene varias modalidades de cierre, y la especificación pide indicar
cuál se usa al comparar resultados:

- `close` recibe una lista explícita de reglas;
- `close_program` recibe el módulo y activa los Programs asociados a verbos
  (@sec:s5.6);
- `IncrementalClosure` mantiene un cierre ya calculado ante seeds nuevos
  (@sec:s5.9).

La orden `run` de la CLI muestra el cierre con Programs activos. El resultado
es Known, con una justificación y un sello por cada derivación. La consulta de
requisitos no figura en esa lista porque no es un operador de cierre. La
especificación la describe como búsqueda y certificado sobre las declaraciones
de reglas.

## La consulta residual: búsqueda dirigida por el objetivo

La consulta residual invierte la dirección. Parte de un objetivo ground y
busca las reglas cuya conclusión coincide con él. Sustituye el antecedente con
esos bindings y sigue hacia atrás por cada evento pendiente. Se detiene en dos
clases de hojas:

- un evento que ya está en la evidencia, que no exige nada más;
- un seed ausente, que se propone como hipótesis si es abducible.

El resultado no es un conjunto de eventos. Es un requisito residual: una
fórmula de seeds que basta para derivar el objetivo, con una prueba por cada
explicación. La consulta no añade nada a Known, no sella y no ejecuta efectos.
@Sec:s6.8 define el requisito y cómo se certifica.

La búsqueda sólo expande las reglas cuya cabeza coincide con un evento
pendiente. Una regla que concluye otra cosa no aporta ramas, salvo que la
cadena hacia atrás la alcance. En eso se parece a la evaluación bajo demanda:
el trabajo depende de la pregunta.

```res {#lst:s5-3-dos caption="Las mismas reglas hacia delante y hacia atrás" run=query}
module Prestamo

entity Person
entity Thing

const ana : Person
const libro : Thing
const tau : PropositionTime

seeded verb member(subject : Person)
seeded verb requests(subject : Person, object : Thing)
seeded verb available(object : Thing)
derived verb eligible(subject : Person)
derived verb lent(subject : Person, object : Thing)

rule membership(person, t) = member(person) @ t <= eligible(person) @ t

rule lending(person, object, t) =
    eligible(person) @ t & requests(person, object) @ t & available(object) @ t
    <= lent(person, object) @ after t

experiment complete {
    seeds {
        member(ana) @ tau,
        requests(ana, libro) @ tau,
        available(libro) @ tau,
    }
    query residual lent(ana, libro) @ after tau
}

experiment partial {
    seeds { member(ana) @ tau, requests(ana, libro) @ tau, }
    query residual lent(ana, libro) @ after tau
}

experiment empty {
    seeds {}
    query residual lent(ana, libro) @ after tau
}
```
::: explanation
Cada experimento muestra las dos direcciones. La línea `Horn` y `Known after
close` vienen del cierre hacia delante sobre las reglas del módulo. La línea
`requirement` viene de la consulta hacia atrás desde `lent`. Con todos los
seeds, el cierre deriva el objetivo y el requisito es `I`. Con dos seeds, el
cierre no llega y la consulta dice que falta `available(libro)`. Sin seeds,
falta el producto de los tres.
:::

En @lst:s5-3-dos las dos respuestas son complementarias. El cierre dice qué se
sigue de lo que hay. La consulta dice qué falta para lo que se quiere. En el
experimento `partial` el cierre deriva `eligible(ana)`, pero no el objetivo.
La consulta aprovecha ese evento derivado y sólo pide el seed que falta.

La línea `Horn` nombra la modalidad del cierre que acompaña a la consulta.
Aquí es el cierre con las reglas explícitas del módulo. En una consulta
residual activa, la salida dice `Active closure`, porque el cierre activa los
Programs asociados (@lst:s5-6-activo). Comparar dos salidas exige mirar antes
qué modalidad produjo cada una.

## Qué detiene a cada una

El cierre es monótono, pero eso no garantiza que termine. Una regla puede
generar `t`, `after(t)`, `after(after(t))` sin fin. La especificación lo dice
así: el cierre caracteriza un objeto matemático aunque no sea finito, y la
ejecución sólo lo devuelve cuando se estabiliza. Por eso los runners de
experimentos exigen un grafo de dependencias acíclico antes de cerrar. Es una
condición suficiente de terminación, no una caracterización.

La búsqueda hacia atrás tiene un presupuesto propio, `SearchLimits`, con tres
contadores:

| Límite | Qué cuenta | Valor por defecto |
|---|---|---|
| `max_depth` | Profundidad, incluida la recursión en antecedentes; como máximo 64 | 32 |
| `max_nodes` | Nodos visitados | 4096 |
| `max_branches` | Ramas creadas, intermedias y finales | 4096 |

: Los contadores de SearchLimits {#tbl:s5-3-limites}

Si la búsqueda agota un límite, devuelve un error y descarta todo el trabajo.
Nunca entrega un resultado parcial como si fuera completo. Esos valores no son
garantías de completitud. La especificación advierte cómo leer cada salida:

- `no explanation` (`required: None`) no demuestra que el objetivo sea imposible en general;
- un error por límite o por ciclo no demuestra que falte una explicación;
- el nombre «residual» no implica suficiencia ni completitud respecto de FOUR.

Ambas respuestas son relativas a la vista de reglas y al procedimiento de
búsqueda. La consulta
residual activa también usa `SearchLimits`, pero sólo para la búsqueda. Su
certificación ejecuta un cierre hipotético que `SearchLimits` no acota; la
terminación de ese cierre queda a cargo del llamador y del entorno acotado.

Los dos mecanismos conviven con los límites de proceso del runner (@sec:s7.2).
Esos límites contienen una ejecución, pero no prueban que termine.
@Sec:s6.11 trata la terminación y la parcialidad con más detalle.
