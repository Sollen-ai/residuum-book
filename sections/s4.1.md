Un sistema de tipos clasifica las expresiones de un programa según la clase
de valores que denotan. Con esa clasificación, el compilador rechaza ciertos
errores antes de ejecutar nada [@pierce2002types]. En Residuum los tipos
cumplen las dos funciones clásicas. Impiden que una regla combine valores que
no encajan. También hacen posible que el cierre y la consulta trabajen sobre
datos ya comprobados. Esta sección explica dónde ocurre esa comprobación y
qué asegura.

La sección no trata el subtipado (@sec:s4.3) ni el tiempo (@sec:s4.4). Ambos
temas aparecen sólo como parte del cuadro general.

## De SurfaceAST a TypedAST

<!-- covers: 1 -->

El pipeline activo es Formal → SurfaceAST → TypedAST → derivación/runtime
(@sec:s1.4). El parser produce un SurfaceAST: un árbol que conserva lo escrito,
pero que todavía no sabe qué significa cada nombre. La elaboración
(`src/elab.rs`) recorre ese árbol y produce un TypedAST (`src/typed.rs`). Sólo
el TypedAST llega al cierre, a las consultas y a la ejecución de efectos.

La elaboración hace tres trabajos a la vez:

- **Resuelve nombres.** Cada identificador pasa a ser una constante, un
  parámetro de regla o un verbo declarado. Un nombre que no resuelve es un
  error, por ejemplo `unknown verb` o `unknown rule term`.
- **Asigna tipos.** Cada término del TypedAST tiene un tipo (`Type`): una
  entidad, `Set T`, un opcional `T?` o `PropositionTime`. Los parámetros de
  regla reciben su tipo por inferencia a partir de los verbos (@sec:s4.5).
- **Comprueba compatibilidades.** Cada argumento debe ser asignable al tipo
  que declara el verbo en esa posición. El número de argumentos debe coincidir
  con la aridad del verbo.

El orden de las declaraciones importa. El elaborador lee el módulo de arriba
abajo. Un verbo debe declararse antes que las reglas que lo usan, porque la
regla se comprueba contra la firma del verbo. La única resolución diferida es
la asociación de un verbo con un Program o una regla (`= program P`): se resuelve al
final, cuando ya existen todas las reglas y todos los Programs.

## Verbos y eventos tipados

<!-- covers: 2 -->

Un verbo es la declaración central de un dominio. Su firma da un nombre a
cada argumento y un tipo a cada nombre:

```text
seeded verb sells(subject : Person, object : Thing, recipient : Person)
```

Cada verbo tiene además una clase: `seeded`, `derived` o `effect`. La clase
dice de dónde viene un hecho de ese verbo:

- un verbo `seeded` recibe hechos de entrada, en `seeds`;
- un verbo `derived` sólo se concluye mediante reglas;
- un verbo `effect` también se concluye mediante reglas y, además, describe un
  cambio de estado (@sec:s7.4).

Un evento es la aplicación de un verbo a argumentos en un instante:
`sells(juan, car, pedro) @ tau`. En el TypedAST, un evento lleva cuatro
datos que forman su identidad lógica: el verbo, los argumentos, el tiempo
proposicional y la polaridad. La polaridad distingue el evento positivo de
su negación evidencial, escrita `~sells(...)`. El evento también lleva la clase
del verbo, pero esa clase no forma parte de la igualdad entre eventos.

La elaboración aplica a los eventos varias comprobaciones propias de su
clase:

- Las entradas de `seeds` deben usar verbos `seeded`.
- Un verbo `derived` no puede tener un cuerpo de efecto.
- Una regla no puede concluir la negación evidencial de un verbo `seeded`.
  El error dice que esa conclusión «must be Derived».
- Un experimento residual exige `seeds`; uno `fourFusion` exige `premises`.
- El tiempo de un evento ground debe ser una constante `PropositionTime`.

Estas reglas no son de estilo. Separan lo que el usuario afirma de lo que el
programa concluye. Un seed nunca se confunde con una conclusión, y una
conclusión negativa nunca se presenta como dato de entrada.

## Por qué una regla mal tipada no llega a evaluarse

<!-- covers: 3 -->

La elaboración devuelve un `Result`: o un módulo tipado completo, o un error.
No existe un módulo «parcialmente tipado». El CLI carga el fichero con
`load_formal_module` y sólo ejecuta experimentos sobre el módulo que esa
función devuelve. Si una sola regla o un solo experimento falla, ningún
experimento del fichero se ejecuta.

@Lst:s4-1-rol muestra el caso más simple. El verbo `sells` espera una
`Thing` como segundo argumento. El seed le pasa una persona.

```res {#lst:s4-1-rol caption="Un argumento del tipo de entidad incorrecto" run=expect-error}
module Venta

entity Thing
entity Person

const juan : Person
const pedro : Person
const car : Thing
const tau : PropositionTime

seeded verb sells(subject : Person, object : Thing, recipient : Person)
derived verb sold(object : Thing)

rule sale(seller, object, buyer, t) =
    sells(seller, object, buyer) @ t <= sold(object) @ t

experiment wrongRole {
    seeds { sells(juan, pedro, car) @ tau, }
    query residual sold(car) @ tau
}
```
::: explanation
El seed intercambia el objeto y el destinatario. La elaboración compara cada
argumento con el tipo declarado en esa posición del verbo `sells`. La primera
discrepancia detiene todo el módulo, antes de cualquier cierre o búsqueda. El
mensaje nombra la constante culpable y el tipo que se esperaba.
:::

El error de @lst:s4-1-rol nombra la constante y el tipo esperado. Lo mismo
ocurre con un término dentro de una regla. El mensaje dice entonces «rule
term ... is not assignable to ...». Un parámetro usado en dos posiciones de
tipos distintos produce «conflicting inferred types». En los tres casos, el
error llega antes de que exista un TypedAST.

La consecuencia práctica es una división clara del trabajo. El cierre, la
búsqueda residual y el matching no comprueban tipos de entidad. Confían en que
la elaboración ya lo hizo. Esa confianza tiene límites, y @sec:s4.6 enumera lo
que sólo se detecta al ejecutar.

Los tipos de Residuum son nominales y de primer orden. No hay tipos función,
variables de tipo ni tipos definidos por el usuario más allá de las
entidades. Tampoco hay números, cadenas ni booleanos como tipos primitivos. El
único tipo integrado que se escribe en Formal es `PropositionTime`, y su
constructor `after` no
calcula nada (@sec:s4.4). Por eso un dominio se describe con entidades,
records y verbos (@sec:s4.2 y @sec:s4.10).
