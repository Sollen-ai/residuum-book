La capacidad de modelado mide cuán directamente se escribe el razonamiento de
un dominio. Un lenguaje con buena capacidad de modelado deja que el código siga
la forma del razonamiento original. El programador no tiene que codificar una
idea mediante otra, ni reconstruir a mano una pauta que el dominio da por
supuesta.

El criterio se evalúa por pautas de razonamiento, no por dominios. Cuatro
pautas aparecen en casi cualquier campo normativo o técnico:

- consecuencias que se acumulan y nunca se retiran;
- preguntas sobre lo que todavía falta para llegar a una conclusión;
- reglas generales con excepciones;
- comportamientos que se disparan cuando ocurre un hecho.

Cada pauta puede ser una construcción del lenguaje o una técnica de
codificación. Cuando es una técnica, el modelo pierde parte de su forma. El
lector debe reconstruir la intención, y el lenguaje no puede comprobarla.

## Reglas monotónicas
<!-- covers: 1.1 -->

La primera pauta es la consecuencia acumulativa. En Residuum, una regla
`A <= C` dice que `A` implica `C`. Las reglas son monotónicas: añadir hechos
nunca retira una conclusión. Esa propiedad coincide con muchas pautas de un
dominio. Una compraventa produce un deber de transmitir. Si además consta un
pago, puede añadirse otra consecuencia, pero ninguna se retira.

La negación también respeta esa forma. `~verbo(args) @ t` es negación
evidencial: evidencia de que algo es falso, no la ausencia de una prueba. Un
modelo puede así distinguir «consta que no pagó» de «no consta el pago».

La monotonía tiene un precio. Una regla no puede decir «salvo que conste lo
contrario». Esa pauta pertenece a otra capa, la de defaults. Tampoco puede
decir «si no consta un hecho, entonces». La ausencia de evidencia no produce
ninguna conclusión. @Sec:s6.3 explica el significado del cierre como modelo
mínimo.

Dentro de esa capa, la sintaxis ofrece varias formas para una misma idea:

- `I <= C` declara una conclusión que vale sin requisitos;
- `A <= B -o C` es la cláusula residual: dado `A`, todavía falta `B` para
  concluir `C`;
- `rule rememberOld = remember(oldDate)` especializa una regla general por
  aplicación parcial.

La cláusula residual sirve cuando el dominio enuncia la regla en dos tiempos,
primero lo que ya consta y luego lo que falta. La aplicación parcial sirve
cuando una norma general se fija para una fecha o una parte concretas. Ninguna
de las dos añade una pauta nueva: dan otra forma a la misma regla. @Sec:s5.7
trata la aplicación parcial.

## Requisitos residuales
<!-- covers: 2.1 -->

La segunda pauta es la pregunta inversa: qué falta para llegar a una
conclusión. Muchos lenguajes lógicos sólo responden sí o no. Residuum responde
con un requisito residual, una fórmula de seeds que basta para derivar el
objetivo. El requisito es un valor de primera clase en la salida de la
consulta. @Sec:s6.8 explica cómo se busca y cómo se certifica.

```res {#lst:s2-10-requisito caption="Lo que falta para un préstamo" run=query}
module Prestamo

entity Person
entity Thing

const ana : Person
const libro : Thing
const tau : PropositionTime

seeded verb solicita(persona : Person, cosa : Thing)
seeded verb disponible(cosa : Thing)
derived verb prestado(persona : Person, cosa : Thing)

rule prestamo(persona, cosa, t) =
    solicita(persona, cosa) @ t & disponible(cosa) @ t <= prestado(persona, cosa) @ t

experiment nada {
    seeds {}
    query residual prestado(ana, libro) @ tau
}

experiment soloSolicitud {
    seeds { solicita(ana, libro) @ tau, }
    query residual prestado(ana, libro) @ tau
}
```
::: explanation
La regla `prestamo` exige una solicitud y la disponibilidad de la cosa. Sin
seeds, el requisito es el producto de los dos seeds. Con la solicitud, el
requisito es sólo la disponibilidad. La respuesta no dice «falso»: dice qué
evidencia completaría el préstamo.
:::

@Lst:s2-10-requisito muestra la diferencia con un sí o un no. En el
experimento `soloSolicitud`, Horn no deriva el préstamo. La consulta
devuelve, además, la evidencia que falta. El requisito no entra en Known ni
recibe sello. Es una hipótesis, separada de los hechos.

El harness `LegalAbduction` aplica esa pauta a un caso jurídico. Su objetivo
es la entrega de un coche tras una compraventa. Con dos acuerdos, el de precio
y el de objeto, obtiene tres respuestas:

| Evidencia en Known | Requisito |
|---|---|
| ninguna | ambos acuerdos, como producto |
| el acuerdo de precio | el acuerdo de objeto |
| ambos acuerdos | `I` |

: Requisitos del harness jurídico {#tbl:s2-10-harness}

`I` no significa que Known esté vacío. Significa que no falta nada. El
harness tiene límites declarados: dos niveles de expansión de reglas y una
sola solución. Una búsqueda más profunda o varias alternativas producen un
error explícito. Comprueba la minimalidad por inclusión sólo en sus ejemplos
positivos.

El harness también comprueba cada explicación de otra manera. Construye un
cierre hipotético con copias de la evidencia y de las hipótesis. Verifica que
ese cierre derive `give` y el objetivo final, con sus tiempos. El programa
y la evidencia reales quedan intactos, y no se ejecuta ningún efecto. En este
harness sólo son abducibles los dos acuerdos, y sólo en forma positiva. Un
`effect` requerido se resuelve mediante reglas; no se abduce.

## Defaults y excepciones
<!-- covers: 3.1 -->

La tercera pauta es la regla general con excepciones. El derecho la usa
constantemente: una compraventa produce el deber de entregar, salvo que se
pactara una reserva de dominio. Residuum la escribe con defaults, una capa no
monotónica separada de las reglas:

- `supernormal r`: la regla `r` se aplica por defecto;
- `blocked when C`: salvo que se cumpla `C`;
- `exception r to D when C`: `r` derrota al default `D` cuando se cumple `C`.

```res {#lst:s2-10-default caption="Un default bloqueado mientras se aplica su excepción" run=run}
module Ventas

entity Fact
entity Package
const Plain : Package
const Retention : Package
const ventaNormal : Fact
const ventaReserva : Fact
const tau : PropositionTime

seeded verb sale(id : Fact)
seeded verb retentionAgreed(sale : Fact)
derived verb selected(sale : Fact, package : Package)

rule normalSale(saleId, t) = sale(saleId) @ t <= selected(saleId, Plain) @ t
rule retentionSale(saleId, t) = sale(saleId) @ t <= selected(saleId, Retention) @ t

default NormalSale =
    supernormal normalSale
    blocked when
        retentionAgreed(saleId) @ t

default RetentionSale =
    exception retentionSale
    to NormalSale
    when
        retentionAgreed(saleId) @ t

experiment normal {
    seeds { sale(ventaNormal) @ tau, }
    query residual selected(ventaNormal, Plain) @ tau
}

experiment reserva {
    seeds { sale(ventaReserva) @ tau, retentionAgreed(ventaReserva) @ tau, }
    query residual selected(ventaReserva, Retention) @ tau
}
```
::: explanation
El módulo adapta el ejemplo de defaults de la referencia del lenguaje. Sin
reserva, `NormalSale` se aplica y selecciona el paquete `Plain`. Con
reserva, `blocked when` bloquea `NormalSale` y la excepción `RetentionSale`
se selecciona. La salida de `run` informa del estado de cada default y de la
evidencia que lo decide.
:::

@Lst:s2-10-default escribe la pauta casi como se enuncia. La regla general y
su excepción son declaraciones distintas, y la relación entre ellas es
explícita. El lector no tiene que reconstruir la excepción a partir de una
negación en el cuerpo de la regla general.

```prolog {#lst:s2-10-prolog caption="Una excepción con negación por fallo en Prolog" run=none}
paquete(Venta, plain) :- venta(Venta), \+ reserva(Venta).
paquete(Venta, retention) :- venta(Venta), reserva(Venta).
venta(v1).
venta(v2).
reserva(v2).
```
::: explanation
En Prolog, la excepción se codifica con negación por fallo: `\+ reserva(Venta)`
tiene éxito cuando no se puede probar la reserva. La regla general debe
nombrar cada excepción en su propio cuerpo. Añadir una excepción obliga a
editar la regla general.
:::

@Lst:s2-10-prolog muestra la técnica habitual, la negación por fallo
[@clark1978negation]. Allí la excepción vive dentro de la regla general.
Residuum separa ambas, al estilo de la lógica de defaults
[@reiter1980default]. @Sec:s6.9 define la selección.

La capa de defaults tiene un estado declarado. El documento de diseño la
clasifica como **IMPLEMENTED + TESTED** en fixtures seleccionadas. No es una
demostración general del cálculo de defaults, y la consistencia permanece sin
comprobar. Tres límites afectan al modelado:

- las consultas residuales y FOUR rechazan los módulos con defaults;
- la selección no se reevalúa a partir de sus propias consecuencias;
- un miembro controlado por un default no puede asociarse a la vez a un verbo
  mediante `Verb.program`, porque aún no tiene una semántica acordada.

Un default puede apuntar a una regla o a un Program entero. En el caso jurídico
de `Sales`, cada paquete es un Program con tres usos de regla. La selección
entrega al cierre todos los miembros del Program elegido. Los del otro
quedan fuera, aunque sus antecedentes se cumplan. Una regla general del
entorno, como `obligationCreatesRelation`, no pertenece a ningún paquete y
participa en el mismo cierre.

La capa distingue dos maneras de perder. Un default bloqueado no se aplica
porque se cumple su condición de bloqueo. Un default derrotado no se aplica
porque una excepción aplicable lo desplaza, aunque no haya bloqueo. Una
fixture de prioridad comprueba esa diferencia. Así el modelo dice por qué no
se aplicó la regla general, y no sólo que no se aplicó.

## Programs y activación
<!-- covers: 4.1 -->

La cuarta pauta es el comportamiento asociado a un evento: cuando ocurre una
venta, se pone en marcha su régimen. Residuum la expresa asociando un verbo a
un Program, con `seeded verb starts(object : Thing) = program Finish`.
@Sec:s5.6 presenta los Programs como paquetes de reglas.

El cierre con programas activos sigue unas reglas precisas:

- una instancia positiva conocida de un verbo `seeded` o `derived` activa su
  Program una vez por evento lógico;
- la activación fija los parámetros del Program con los argumentos y el tiempo
  del evento;
- el cuerpo de cada regla debe cumplirse todavía en Known;
- una llamada activada persiste: una premisa que llega después puede
  completarla;
- `~sells(...)` no activa el Program positivo, y la mera declaración tampoco;
- las asociaciones de verbos `effect` quedan inactivas.

Esta pauta modela bien una cadena de consecuencias. Una venta produce la
propiedad del comprador, y la propiedad activa su protección frente a
terceros. La fixture `sells_composed_programs.res` encadena así dos
Programs. La versión inline, con reglas ordinarias, produce los mismos eventos
y las mismas sustituciones.

La provenance conserva el nombre de la regla del Program, la sustitución
completa y los testigos del cuerpo. Si el cuerpo no cita el evento que activó
el Program, la activación lo añade a los testigos. Así la explicación de una
consecuencia llega hasta el hecho que la puso en marcha.

La activación tiene sus propios límites. El runner exige un grafo de
dependencias acíclico, incluidas las guardas implícitas de activación. La
ejecución de estados no ocurre en esta capa.

## Veredicto

Residuum escribe directamente las cuatro pautas: consecuencias monotónicas,
requisitos residuales, defaults con excepciones y Programs asociados a
eventos. Cada pauta es una construcción propia, no una codificación. Las capas,
sin embargo, no se combinan libremente: las consultas residuales rechazan los
defaults, la activación exige grafos acíclicos y la capa de defaults sólo está
probada en fixtures seleccionadas. Según este criterio, Residuum ofrece un
desempeño alto: escribe cada pauta con una construcción propia, aunque sus
capas no se pueden mezclar en una misma consulta.
